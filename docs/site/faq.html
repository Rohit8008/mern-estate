FAQ and troubleshooting

Symptoms, causes and fixes for the failures that have actually happened in this codebase, grouped by area.

Each answer names the code that produces the symptom, so you can confirm the cause rather than guess. When you report a problem, quote the requestId from the error body (also the X-Request-Id response header): it finds the exact request in the logs.

Setup and development

The backend crashes on start with a SlowBuffer error.

You are on Node 25. It removed SlowBuffer, which the jsonwebtoken dependency chain (jwa, buffer-equal-constant-time) still uses. Run the backend on Node 20; CI does (.github/workflows/ci.yml). With Homebrew: PATH="/opt/homebrew/opt/node@20/bin:$PATH" npm run dev. The Vite frontend runs fine on newer Node.

The backend exits immediately saying environment variables are missing, or configuration validation failed.

config/environment.js exits if any of JWT_SECRET, REFRESH_SECRET, MONGO_URI, NODE_ENV, MESSAGE_ENCRYPTION_KEY is unset. validateConfig() then requires both JWT secrets to be at least 32 characters and, in production, either APP_DOMAIN or DEFAULT_TENANT_SLUG. The last one catches a quiet failure: with neither, requests fall back to a workspace slugged default that may not exist, and because a query with no workspace throws, the whole API would be down rather than degraded. See the variable table.

MongoDB will not connect locally.

Check the server is actually listening (lsof -nP -iTCP:27017 -sTCP:LISTEN). On macOS mongod --fork is unsupported; start it with mongod --config /opt/homebrew/etc/mongod.conf in a background shell. An Atlas mongodb+srv:// URI whose cluster was deleted fails DNS resolution; point MONGO_URI at a local database instead.

npm install fails with 401 on package fetches.

A user-level ~/.npmrc points at a private registry. Override per command: npm_config_registry=https://registry.npmjs.org npm install. Separately, the frontend's xlsx dependency resolves to a tarball on cdn.sheetjs.com, so installs (and CI) need egress to it; install with --legacy-peer-deps.

The Flutter web app (or a second frontend origin) says "Unable to reach Real Vista" and nothing loads.

The browser is blocking the call under CORS. In development only the Vite and API origins are allowed by default; add the extra origin, comma-separated, to EXTRA_CORS_ORIGINS in backend/.env (for example http://localhost:54321). In production the allowed origins are only FRONTEND_URL and ADMIN_URL; EXTRA_CORS_ORIGINS is ignored there. A native mobile app sends no Origin and is not affected.

A seed or one-off script ran, but the records are invisible in the app.

The script imported a model directly. Tenant scoping is a global Mongoose plugin and only applies to schemas compiled after it is registered; a hoisted import compiles the schema first, so the records are written with no tenantId and the app can never see them. Load models with const { models, inWorkspace, close } = await bootstrapScript() from scripts/_bootstrap.js. It takes --workspace <slug> and refuses to guess when several workspaces exist. Records already written without a tenantId have to be repaired by hand (npm run db:migrate-tenancy stamps documents that have none, but it is a one-time migration; read it first).

An error says "a query ran with no tenant context".

That is the isolation guarantee working. tenantPlugin.js throws rather than run an unscoped query. In a request it means something ran outside the tenant context (for example work started after the response, or a callback that lost async context). In a script, cron job or socket handler, enter a workspace explicitly with runWithTenant, withTenantBySlug or forEachTenant. For deliberate cross-tenant work use runWithoutTenantScope('why'), and never build a tenantId filter by hand. A related error says a query asked for a different tenant than the request's; that is also deliberate.

My test calls a controller directly and gets an empty response with no error.

asyncHandler does not return its promise, so await controller(req, res, next) resolves before any database work finishes. Either go through HTTP with supertest (which needs a session), or call the handler without awaiting and poll until res.body is set or next fires.

Creating a second user without a phone number fails with a duplicate key error.

An obsolete unique index survived. Mongoose never drops an index it no longer declares, so the old phone_1 (plain unique and sparse, which still collides on null) outlives the model's partial index tenant_phone_unique_string. The same class of problem is why db:migrate-tenancy drops the old global unique indexes (a leftover email_1 makes the second agency's duplicate email fail). Drop the stale index (db.users.dropIndex('phone_1')) or run User.syncIndexes() once.

I ran db:seed-fresh and lost data.

It is destructive with no confirmation prompt: it wipes the collections of the workspace it runs in and reseeds sample data (keeping the first admin). Only use it on a throwaway database. To empty a real workspace safely, scripts/purgeWorkspaceData.js --workspace <slug> --confirm writes a JSON backup first and keeps the tenant, admins and roles.

Sign-in and sessions

Sign-in says "invalid email or password", but the credentials are right.

Usually the wrong workspace. The same email can exist in two agencies, and an unauthenticated request with no workspace falls back to DEFAULT_TENANT_SLUG. Enter the workspace name on the sign-in screen (sent as x-tenant). A name that does not exist answers 404 WORKSPACE_NOT_FOUND ("There's no workspace called ...") instead of using the default. If the account is locked the message says so: "Account locked. Try again in N minute(s)". Five wrong passwords (MAX_LOGIN_ATTEMPTS) lock the account for 15 minutes (LOCKOUT_DURATION), and the lock is checked before the password, so the right password does not help until it lapses.

Every request returns 401 and the app keeps sending me back to sign-in.

Work down this list.

  • Cookies not stored. In production the cookies are SameSite=None; Secure, so the site must be served over HTTPS. Over plain HTTP the browser rejects them. If the app and API are on different origins, FRONTEND_URL must exactly match the app's origin or CORS blocks credentialed calls.
  • The server's secrets changed. Changing JWT_SECRET or REFRESH_SECRET invalidates every existing token; signed-in users are signed out once their access token lapses (up to 15 minutes). That is expected, not a bug.
  • The refresh token was replayed. A refresh token that is validly signed but not on the user's stored list is treated as theft and every session of that user is wiped. Two tabs refreshing with the same cookie at once can trigger it; the web client serialises refreshes for this reason.
  • The cookie outlived its token. Cookie lifetimes now come from ACCESS_TOKEN_EXPIRY / REFRESH_TOKEN_EXPIRY, so they cannot drift from the JWT. A cookie from before that change could.
  • The account is disabled or the password changed. inactive and suspended accounts are rejected on every request, and access tokens issued before a password change are refused ("Session expired. Please log in again.").
  • Sockets only: "Session predates workspaces. Please sign in again." means the token has no tid claim; sign in once.

A write fails with 403 CSRF_TOKEN_INVALID or CSRF_COOKIE_MISSING.

Every non-GET call made with a session must send an X-CSRF-Token header equal to the csrf_token cookie. CSRF_TOKEN_INVALID: the header is missing or stale; the token rotates on sign-in, refresh and act-as, so re-read the cookie (or GET /api/auth/csrf) at call time and retry once. CSRF_COOKIE_MISSING: the session predates the CSRF check; sign in again. For a cross-origin deployment the proxy or CORS preflight must allow the header. Scripts using curl must send both the cookie jar and the header. See Authentication.

Sign-out said it worked, but the session still came back.

This was a real bug during operator "acting as" sessions: the user lookup ran in the customer's workspace, found nothing, skipped revoking the refresh token and still answered "signed out", leaving it valid for 30 days. Sign-out is now pinned to the caller's home workspace (inHomeTenant). Any new code that looks up the caller (User.findById(req.user.id), a security-log write about a session) must be pinned the same way, because an unpinned lookup fails silently as "nothing to do".

As a platform operator, my edits fail with "This view is read-only".

You are in an acting-as session. By design it is read-only: tenancy/readOnlyWhileActing.js blocks every non-GET except session-level calls (stop-acting, act-as, refresh, sign-out and your own Terms acceptance). Support can see what the customer sees but not edit their records, so an agency's audit trail always names a person at that agency. Leave with POST /api/platform/stop-acting and make changes in your own workspace.

An invitation link says it is no longer valid, or "a newer invitation was sent".

Links expire after 7 days and work once. Expired, used and unknown tokens all answer the same 404 on purpose. If you open an older email after the invitation was re-sent, the answer is 410 INVITE_REPLACED: open the newest email. If none work, a workspace admin (or a platform operator via POST /api/platform/tenants/:id/invite for the first admin) can send a fresh one.

The password-reset code never arrives.

The request always answers "If that address has an account, a code is on its way", whether or not the address exists, so the response cannot tell you. Check that SMTP is configured (SMTP_USER and SMTP_PASS; otherwise no transport exists), that you entered the right workspace, and the spam folder. The code is six digits, valid for 10 minutes and dies after 5 wrong guesses. In development with no SMTP configured the response includes devOtp.

API behaviour

I got 409 VERSION_CONFLICT.

Someone saved the record after you loaded it. Listing and client edits send expectedUpdatedAt, the write is conditional on it, and the answer carries details.currentUpdatedAt. The web form offers "Load their version" or "Keep mine" (resend without the guard). A caller that sends no version (mobile app, scripts) is last-write-wins and never sees this. Other 409s are different: creating a lead whose phone or email exists returns data.duplicate and canForce: true (use ?force=true if it is genuinely a second person on a shared number), and deleting a category in use, or removing a field that holds values, returns a count you can override with ?force=true.

I got 402 PLAN_LIMIT.

The workspace's plan caps users, listings, monthly import rows or storage, and the create was refused. 402 (not 403) because it means "your plan doesn't cover this", not "you may not". Limits gate creation only; reads and existing data are never locked. The message names the cap and the way out. Check GET /api/tenant/usage, or ask the operator to move the plan or raise the cap. Changing a figure in tenancy/plans.js re-caps every live workspace on that plan.

My import was rejected or only partly written.

Both importers validate every row first, then write in batches and return per-row results. The lead importer accepts at most 5000 rows per file ("import up to 5000 at a time"). Row errors are capped at 200 in the response (rowErrorsTruncated: true says the list was cut; the counts stay exact). Rows are metered against maxImportRowsPerMonth: the importer reserves rows before writing and releases what did not land, and a request that would pass the allowance answers 402. The meter rolls over by the daily import-usage-reset job. Imported leads that duplicate an existing phone match on the derived phoneKey; if you migrated old data, run npm run db:backfill-phone-keys or older leads are invisible to the duplicate check.

I get 429 RATE_LIMITED.

The general limit is 1000 requests per 15 minutes per signed-in user (per IP if signed out), 20 per 15 minutes on credential endpoints, 30 uploads per minute. Behind a proxy, check that production trust proxy (set to one hop) matches your topology; if the limiter sees the proxy's IP, everyone shares one bucket. On several instances without REDIS_URL each instance counts separately (limits are looser than configured, not tighter). Honour Retry-After.

A list endpoint returns an array on one call and an object on another.

GET /api/owner/list and GET /api/buyer-requirements page only when page is passed; without it they return a bare array (the mobile app and the listing form depend on it). With page you get { success, data, page, limit, total }. limit is capped at 500. Sort on the server with sort=key:asc|desc using the endpoint's allowed keys.

Responses look like { "_enc": true, "iv": ..., "data": ... } and the app shows nothing.

The server has ENCRYPT_API_RESPONSES=true. The web client decrypts only if it was built with VITE_API_RESPONSE_SECRET equal to API_RESPONSE_SECRET; otherwise the console shows "Received encrypted response but VITE_API_RESPONSE_SECRET is not configured". The mobile app cannot decrypt at all. Turn encryption off, or rebuild the web app with the matching secret. See API conventions.

A workspace rule makes a save fail with 400.

A rule that calls veto('...') refuses the operation and its message reaches the user as a 400. Any other error inside a rule is logged and the rule is skipped, so "my rule does nothing" usually means it threw (look for the log line) rather than vetoed. Rules are named implementations registered in plugins/builtin.js; config selects them, never carries code.

Sharing and public pages

A share link does not work for the buyer.

  • "This link is not valid" (404): wrong or mistyped token. Unknown and never-existed tokens look identical so the endpoint cannot be used to enumerate them.
  • 410: the link expired (default 30 days from creation) or was revoked. Create a new one.
  • 401 with passcodeRequired: the link has a passcode (min 4 characters). The page sends it as x-share-passcode; a wrong one is logged and answers 401 again.
  • Too many attempts: the open endpoint allows 60 requests per 15 minutes per IP.
  • The property is missing from the page: a deleted listing drops out; and you can only share listings you can see (createShare re-reads through listingScope).
  • Owner contacts, internal notes and commission are never shown on a share page; forRecipient() is an allowlist.

A public page such as /privacy or /terms returns 404 (or crawlers show the home page's title).

The web server lacks the SPA fallback. The build writes real files like dist/privacy/index.html, so the server must use try_files $uri $uri/ /index.html;. Without $uri/ the per-page HTML is skipped and every crawler sees the home page's tags; without any fallback a deep link is a 404. Also confirm VITE_SITE_URL was set at build time: if not, canonicals and sitemap.xml use the default https://realvista.duckdns.org. See Deploy and operate.

I changed a VITE_* value and nothing happened.

Vite compiles these into the bundle at build time. Rebuild (and redeploy frontend/dist) after any change. In Docker they are build args; compose passes only the two Cloudinary values. On the production host, build in place so the values in frontend/.env.production.local are used.

Data and display

Areas show "sq ft" or the rupee sign for a workspace that uses something else.

A call site is bypassing the locale layer. Never construct Intl.NumberFormat in a component and never hardcode ₹, en-IN or sq ft. Use the formatters in frontend/src/utils/currency.js; TenantProvider pushes the workspace locale in via setLocaleConfig(). There are six area units (sqft, sqyard, sqm, acre, cent, guntha) and all six must work, not the two a ternary covers.

A screen shows the wrong name or a missing translation.

A workspace's own rename of a screen beats a translation (useScreens.js compares label with defaultLabel). Translations are JSON files in frontend/src/i18n/locales/, found by glob; i18n/__tests__/locales.test.js fails the build on a missing key or a dropped {{placeholder}}. Screen ids are a contract with stored workspace settings: never rename one.

A Tailwind colour does not appear.

Interpolated class names such as `text-${color}-400` never work: Tailwind scans source as plain text, so the class is never emitted. Write every class as a complete literal string, usually via a lookup table keyed by variant.

A lead's temperature or score looks wrong.

client.calculateScore() is the only place the score is computed, and it runs on create, update, deal-stage change and nightly. Temperature follows the score unless someone set it by hand, which sets temperatureManual and pins it (choose Auto, or send temperature: "auto", to release the pin). Won and lost leads are never rescored, so past reports do not change.

A lead got another follow-up email after being marked won.

It should not. stopSequencesForClient() is called synchronously from the deal-stage change so there is no gap, and the job stops an enrollment when the lead is won, lost or deleted. If it happened, check that the stage change went through updateDealStage and not a direct database write.

Deployment

Works locally but not behind a reverse proxy.

  • Forward /api, /uploads and /socket.io (with WebSocket upgrade) to the Node process.
  • Pass X-Forwarded-For / -Host / -Proto. Production trusts exactly one proxy hop.
  • Terminate TLS: Secure cookies are not set over HTTP.
  • Subdomain routing needs APP_DOMAIN and a wildcard DNS and certificate; a single-label subdomain only, and www app api admin auth static cdn assets localhost are reserved.

Uploads fail with permission denied in Docker.

The container runs as the node user (uid 1000). A host bind mount keeps the host's ownership and the app cannot write to it. Use the named volume compose defines (uploads_data), or chown the host path to uid 1000.

An upload is rejected as "not a valid image" although it opens fine.

Uploads are judged by their real content (magic bytes), never by file extension or declared type. A renamed file, an SVG, or a corrupt file is refused. Images accept JPEG, PNG, GIF and WebP; documents accept PDF, DOCX, XLSX, PPTX, ZIP, JPEG and PNG (plus legacy DOC, XLS, PPT). Size limits are 10 MB per image, 25 MB per audio file, and the plan's storage cap (402) applies first.

PM2 restarts are slow or kill requests mid-flight.

The ecosystem file sets kill_timeout: 15000, longer than the app's 10-second default drain (SHUTDOWN_TIMEOUT_MS), and the app sends the ready signal that wait_ready waits for. If you raise SHUTDOWN_TIMEOUT_MS, raise kill_timeout with it.

Live updates or presence work for some users but not others.

You are probably running more than one process (PM2 cluster mode after changing the shipped instances: 1, or several hosts). There is no Socket.IO adapter, and presence is an in-process map, so an event emitted in one process never reaches sockets held by another. Run one process, or add an adapter first. REDIS_URL shares the rate limiter and cache invalidation, not sockets.

Restoring a backup fails.

Dumps from npm run db:backup are gzipped and restore with npm run db:restore -- --from <name> --confirm (production also needs ALLOW_PRODUCTION_RESTORE=true, and you must type the database name). The compose backup service now dumps with --gzip and the same folder naming, so restore.js can read them (dumps from an older compose file were not gzipped: restore those with mongorestore --drop directly). Both need MongoDB Database Tools installed.

The mobile build fails in Gradle.

Use Flutter 3.24.5 and JDK 17. A newer Flutter's Gradle plugin needs Gradle 8.14 and fails inside AGP 8.1.0, and it rewrites gradle.properties, analysis_options.yaml and pubspec.lock (check git status). Details in Mobile app. If a release APK cannot reach the server, it was built without --dart-define=API_BASE_URL and is pointing at localhost.

Production errors and security events are not in any log.

Without OPENOBSERVE_USERNAME and OPENOBSERVE_PASSWORD the logger writes to stdout only and drops everything else; production prints a warning at boot. Set them, or collect stdout elsewhere. The security log in MongoDB (180-day TTL) is separate and always written. Sentry is not wired (utils/sentry.js is a no-op stub).
