Mobile app

The Flutter companion app in mobile/: how it is structured, how it signs in against the same cookie API, how to build and run it, and how the Android APK is published to /app/ and the /download page.

What it is

mobile/ is a separate Flutter project (realvista_crm, version 1.0.4+5 in pubspec.yaml) that talks to the same backend as the web app. There is no mobile-specific API and no push-notification service: real-time updates come over Socket.IO while the app is open. The Android build is distributed as a sideloaded APK from the web app's /download page; it is not on the Play Store, and nothing in the repository shows an iOS build having been produced (Xcode is needed and the release notes list iOS signing as still to do).

Which Flutter to use

Use Flutter 3.24.5, not a newer one. Current Flutter's Gradle plugin needs Gradle 8.14 or newer, and --android-skip-build-dependency-validation does not rescue it: the build fails later inside AGP 8.1.0. Closing that gap is an Android toolchain migration across all plugin dependencies, not a version bump. Running a newer flutter against this project also rewrites android/gradle.properties, analysis_options.yaml and pubspec.lock in place; check git status afterwards and revert if you did not mean to migrate (mobile/RELEASE.md).

A working Android build environment needs the SDK path and a JDK that Gradle 8.3 can use (JDK 17; the newest JDK is too new). Example, adjusting paths to your machine:

export PATH="$HOME/sdks/flutter-3.24.5/bin:$PATH"
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
export ANDROID_SDK_ROOT="$ANDROID_HOME"
export JAVA_HOME=$(/usr/libexec/java_home -v 17)

The shell has four bottom tabs (Home, Leads, Properties, Activities), a centre quick-action button and an overflow "More" screen, pruned by the user's permissions the way the web sidebar is (canProvider mirrors PermissionsContext.jsx: admins short-circuit to all, employees fetch their permission map, other roles get none). Every API wrapper converts a DioException into an AppFailure so UI code never inspects status codes.

How it authenticates

The mobile app has no token handling of its own. It uses exactly the cookie protocol the browser uses (Authentication and sessions); the only differences are where the cookies live and how the CSRF token is obtained.

  1. Cookie storage. On native platforms ApiClient.create builds a PersistCookieJar backed by files under the app-support directory (.cookies/), attached through Dio's CookieManager, so the 30-day session survives app restarts. On Flutter web there is no dart:io; the browser stores and sends the cookies and the adapter is only told withCredentials = true.
  2. Workspace. WorkspaceStore keeps the chosen workspace slug (file workspace.txt; memory only on web) and an interceptor sends it as x-tenant on every request unless the call names one itself (the login screen checks a typed name via GET /api/tenant/lookup with an explicit header). Normalised to lower case, letters, digits and dashes, the same rule as the web's utils/workspace.js. A session carries its own workspace and the server trusts that over the header, so it only decides where sign-in and "forgot password" look.
  3. Sign in. POST /api/auth/signin with email and password; the response user becomes the auth state. At launch AuthController.bootstrap() calls GET /api/user/me: an authentication failure means signed out; any other failure shows an "Unable to reach Real Vista" screen with a retry rather than a login form.
  4. Refresh. A 401 on any non-auth call triggers one POST /api/auth/refresh (concurrent 401s share one in-flight call, because the backend treats a re-presented refresh token as theft and wipes every session) and the original request is replayed once. Sign-in, refresh and signup paths are never retried.
  5. CSRF. A Flutter web build cannot read document.cookie, so instead of reading the cookie the interceptor asks the server: GET /api/auth/csrf returns the value the jar or browser just sent. It is cached, attached as X-CSRF-Token to every non-GET call except the unauthenticated writes (sign-in, signup, refresh, csrf, password OTP and reset), and refetched once on 403 CSRF_TOKEN_INVALID (the token rotates on refresh and act-as).
  6. Sign out. POST /api/auth/signout, plus signout-all on request, then clearSession() deletes the jar so a stale refresh cookie does not linger. On web clearing is a no-op; the server's Set-Cookie expires the cookies.
  7. Terms gate. After sign-in the app asks the backend whether the current Terms version still needs accepting. If so, the legal-acceptance screen is the only reachable route until accepted (this mirrors LEGAL_VERSION). If the check itself fails or times out (8 seconds) the user is let in and asked next launch: failing open beats locking someone out of their CRM over a status call.
  8. Socket.IO. The server authenticates the handshake from the access_token in the Cookie header. socket_io_client does not share Dio's jar, so on native socketCookieHeaders() copies the jar's cookies into an explicit header; on web the browser attaches them itself. The app listens to message:new, conversations:update, listing:update, owners:changed and notification:new.

The mobile client has no decoder for encrypted responses, so on native platforms it sends X-Client: mobile and middleware/encryptResponse.js answers those requests in plaintext even when ENCRYPT_API_RESPONSES=true. This needs an app build that includes the header; older builds still break against an encrypting server.

Because the app is cookie-only, a client of this API written elsewhere needs a cookie jar and the CSRF header, not a bearer token.

Pointing the app at a backend

Env.apiBaseUrl resolves in this order: the compile-time --dart-define=API_BASE_URL=...; else http://localhost:3000 for web; else http://10.0.2.2:3000 on Android (the emulator's alias for the host machine); else http://localhost:3000. A release build must always set API_BASE_URL, or it will try to reach localhost on the user's phone.

# debug build against a backend on your LAN (a phone's localhost is the phone)
flutter build apk --debug --dart-define=API_BASE_URL=http://<lan-ip>:3000

# or hot reload over wireless debugging
flutter run --dart-define=API_BASE_URL=http://<lan-ip>:3000
  • The backend already binds 0.0.0.0. A native Dio client sends no Origin, so CORS does not apply to it; EXTRA_CORS_ORIGINS matters only for the web target (flutter run -d chrome needs the Flutter web dev port added, or every call is blocked and the app shows "Unable to reach Real Vista").
  • Cleartext HTTP: Android refuses it by default for apps targeting API 28 and above. Debug and profile builds include network_security_config.xml (under android/app/src/{debug,profile}/res/xml/) permitting it; release builds do not and keep the default refusal. iOS has no equivalent exception; use an HTTPS tunnel for iOS testing.
  • Install without a cable: serve build/app/outputs/flutter-apk/ with any static server on the LAN and open the APK URL on the phone.
  • ApiClient branches on kIsWeb. Never call path_provider's getApplicationSupportDirectory() unconditionally; it throws MissingPluginException on web.

Build, test, regenerate assets

cd mobile
flutter pub get
flutter analyze
flutter test

# debug APK / release APK (set API_BASE_URL for release)
flutter build apk --debug   --dart-define=API_BASE_URL=http://<lan-ip>:3000
flutter build apk --release --dart-define=API_BASE_URL=https://your-api-domain

# Play Store bundle, iOS archive (needs your own signing, see below)
flutter build appbundle --release --dart-define=API_BASE_URL=https://your-api-domain
flutter build ipa       --release --dart-define=API_BASE_URL=https://your-api-domain

# after changing assets/icon/*
flutter pub run flutter_launcher_icons
flutter pub run flutter_native_splash:create

Fonts are bundled (assets/google_fonts/, with the OFL licence registered) and GoogleFonts.config.allowRuntimeFetching is false. Leaving fetching on would download missing weights from fonts.gstatic.com at runtime, handing a third party each user's IP address, which the privacy policy does not disclose. test/bundled_fonts_test.dart guards this.

RELEASE.md: what is done, what is left

Done: app identity on both platforms; icon and splash generated from the web brand mark (frontend/public/pwa-512.svg, sources in mobile/assets/icon/); the INTERNET permission added to the Android release manifest (only debug and profile builds get it for free, so every network call in a release build would have failed silently) plus package-visibility <queries> for call, email and web actions; Android signing scaffold that reads android/key.properties and falls back to debug signing so unsigned local builds still work.

Still needs your own accounts or secrets:

  1. Point release builds at the real backend with --dart-define=API_BASE_URL, and make sure that origin is allowed (FRONTEND_URL / ADMIN_URL / EXTRA_CORS_ORIGINS) for the Socket.IO origin check if applicable.
  2. Android release keystore: generate one with keytool, copy android/key.properties.example to android/key.properties (git-ignored) and fill storePassword, keyPassword, keyAlias, storeFile.
  3. iOS: open ios/Runner.xcworkspace (not the .xcodeproj), set the Apple Developer Team under Signing and Capabilities; the bundle id must match a registered App ID.
  4. minifyEnabled false is deliberate in android/app/build.gradle. proguard-rules.pro has starter rules; if you enable R8, test a real release build on a device first, because minification bugs are runtime-only and do not show up in flutter analyze or flutter test.
  5. Store listing assets (screenshots, feature graphic, privacy-policy URL) do not exist yet.

Publishing the APK

Until the app is on a store, releases go to the web host and the /download page reads the latest one. A new version needs no web deploy.

bump version: in pubspec.yaml
→
./scripts/publish-apk.sh "notes"
→
APK, then latest.json, to the server
→
/download shows it

mobile/scripts/publish-apk.sh (run from mobile/):

  1. Requires android/key.properties; refuses to run without it, because releases must be signed with the release key.
  2. Reads version: 1.0.4+5 from pubspec.yaml: the part before + is the version, after it the build number.
  3. Builds with $FLUTTER (the script uses FLUTTER= if set, else flutter on PATH, else ~/sdks/flutter-3.24.5 or ~/development/flutter-3.24.5, and exits with an error if none exist) and --dart-define=API_BASE_URL (default https://realvista.duckdns.org; override with API_BASE_URL=). Then restores the committed pubspec.lock with git checkout, since 3.24.5 re-resolves it.
  4. Names the file realvista-<version>.apk and writes latest.json: 
    { "version": "1.0.4", "build": 5, "file": "realvista-1.0.4.apk",
  "sizeBytes": 0, "sha256": "...", "releasedAt": "2026-10-01T00:00:00Z", "notes": "..." }
    (sizeBytes, sha256 and releasedAt are computed from the built file and the clock.)
  5. Uploads over SSH: ssh realvista 'mkdir -p ~/sites/realvista-app', then rsync of the APK first and latest.json second, so the page never points at a file that is not there yet. It needs a realvista host entry in ~/.ssh/config.

The web server must serve ~/sites/realvista-app/ at /app/, as static files that never fall through to the SPA (the PWA service worker also excludes /app/ from its navigation fallback). /app/ is also disallowed in the generated robots.txt.

The /download page

frontend/src/pages/DownloadApp.jsx is a public route and one of the six pages prerendered for SEO (Deploy and operate). In the browser it fetches /app/latest.json with cache: 'no-cache' (a plain fetch, because it is a static file and not an /api route), shows the version, size in MB, release date, notes and SHA-256, and links to /app/<file>. If the fetch fails it shows an "unavailable" message. It detects iOS and Android from the user agent to tailor the wording.

The release keystore is the one thing you cannot regenerate. Android only installs an update signed with the same key as the installed app; losing the key means every user must uninstall and reinstall. RELEASE.md records the keystore at ~/.realvista/realvista-upload.jks (password in android/key.properties, a copy in ~/.realvista/key.properties.backup). Back both up somewhere safe, and use the same key as the Play Store upload key later. Never commit key.properties.

Testing and gotchas

  • Tests in mobile/test/: widget test, bundled fonts, workspace login, legal acceptance, follow-up refresh, analytics report.
  • PageView(children: [...]) mounts every page eagerly. In a multi-step form (the six-step listing wizard in features/listing_form/), find.byType(TextField).at(N) indexes across all steps at once and silently targets the wrong field. Give fields an explicit Key and find them with find.descendant(of: find.byKey(...), matching: find.byType(TextField)).
  • GridView.count(childAspectRatio:) scales cell height with viewport width. A ratio tuned for a 390 px phone overflows on a wider surface (the default widget-test surface is 800x600). Use SliverGridDelegateWithFixedCrossAxisCount(mainAxisExtent: ...) for KPI cards and stat tiles so height does not depend on width.
  • Override tester.view.physicalSize to a realistic phone size (390x844) in tests that depend on layout.
  • connectivity_plus and the socket connection do not work fully inside flutter test, but neither crashes it: the online provider assumes online until told otherwise and the socket connect is fire-and-forget.
  • Entering text through adb shell input text on an emulator drops characters and swallows spaces on longer strings; type in short chunks, use KEYCODE_TAB to move between fields and re-screenshot before submitting.
  • If "the app isn't working" against a local backend, check the backend is running on Node 20 first (FAQ).
