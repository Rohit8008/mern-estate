Deploy and operate

Environment variables, Docker, Render and PM2 deployment, the web-server rules the SPA and SEO pages need, health checks, shutdown, backups, migrations, logs, scheduled jobs, scaling, tests and a release checklist.

What runs where

One Node process (backend/index.js) serves the API on /api, Socket.IO, uploaded files on /uploads and, when frontend/dist exists, the built web app with an SPA fallback. MongoDB is the only required dependency. Redis, SMTP, Twilio, Cloudinary and OpenObserve are optional and degrade gracefully (table below). The frontend's VITE_* values are compiled into the bundle, so they are fixed at build time, not read at runtime.

Backend environment variables

Read from backend/.env (loaded by config/environment.js via dotenv) or the real environment. The process exits at boot if one of the five required variables is missing; validateConfig() adds the production checks noted below. Only variables read by code are listed; backend/.env.example also carries names nothing reads (see Stale files).

Deployment options

Docker

The Dockerfile is two stages on node:20-alpine: stage 1 runs npm ci --legacy-peer-deps and npm run build in frontend/ with build args VITE_CLOUDINARY_CLOUD_NAME, VITE_CLOUDINARY_UPLOAD_PRESET, VITE_API_URL and VITE_SOCKET_URL; stage 2 installs backend production dependencies, copies backend/ and the built dist to /app/frontend/dist, creates uploads, runs as the non-root node user and starts node index.js on port 3000 with NODE_ENV=production.

  • docker-compose.yml builds that image, loads backend/.env, forces NODE_ENV=production, PORT=3000, FRONTEND_URL=http://localhost:3000 and defaults OPENOBSERVE_URL to host.docker.internal:5080. Change FRONTEND_URL for a real domain.
  • Uploads live in the named volume uploads_data mounted at /app/uploads. A named volume (not a bind mount) is used because the container runs as uid 1000 and Docker initialises a named volume with the image path's ownership.
  • A backup service on the mongo:7 image runs mongodump every 24 hours into backups_data and keeps BACKUP_RETENTION_COUNT (default 7). It is a separate service because node:20-alpine has no mongodump. See the compatibility warning under Backups.
  • Only VITE_CLOUDINARY_* are passed as build args by compose. To bake in VITE_API_RESPONSE_SECRET or VITE_SITE_URL add them to the compose args and the Dockerfile ARG list.

Render (render.yaml)

Two services: mern-estate-api (Node, cd backend && npm install, node index.js, health check /api/health/startup, generated JWT_SECRET and REFRESH_SECRET, others set in the dashboard) and mern-estate-client (static site built from frontend/, with /api/* and /uploads/* rewrites to the API and an SPA rewrite to /index.html).

The blueprint declares DEFAULT_TENANT_SLUG, APP_DOMAIN and FRONTEND_URL as dashboard-set variables (sync: false): in production the API exits at boot without one of the first two, and FRONTEND_URL must be a full origin such as https://... (the client service's host property has no scheme, so it is no longer used). MESSAGE_ENCRYPTION_KEY is generated once by Render, and the sender is SMTP_FROM. Not verified by an actual Render deploy.

PM2 (backend/ecosystem.config.js)

  • App mern-estate-api, script: index.js, instances: 1, exec_mode: 'fork', max_memory_restart: 1G, --max-old-space-size=1024, kill_timeout: 15000, logs under logs/pm2-*.log. Scripts: npm run pm2:start | pm2:stop | pm2:restart | pm2:logs | pm2:monit.
  • wait_ready: true is honoured: index.js calls process.send?.('ready') once the server is listening (listen_timeout 30 s).
  • kill_timeout: 15000 is longer than the app's default SHUTDOWN_TIMEOUT_MS (10 s), so PM2 does not SIGKILL a drain in progress. Keep it above that value if you raise the timeout.
  • The deploy block is marked as a template with placeholders (your-server.com, your-username); fill them before using pm2 deploy.
  • Single instance and Socket.IO. Neither a Socket.IO adapter nor sticky sessions is configured (backend/package.json has no @socket.io/redis-adapter), and presence is an in-process map, so the ecosystem file runs one process in fork mode. Before raising instances or running several hosts, add an adapter.

Web server expectations

There is no nginx file in the repository; the code defines what a front proxy must do:

  • Proxy /api, /uploads and /socket.io (with WebSocket upgrade headers) to the Node process on port 3000, and send X-Forwarded-For / X-Forwarded-Host / X-Forwarded-Proto. Production sets trust proxy to 1, i.e. exactly one proxy hop; rate limiting and security logs use the client IP derived from it.
  • If nginx serves frontend/dist itself, it must fall back with try_files $uri $uri/ /index.html;. The build writes real per-page HTML (dist/privacy/index.html, dist/terms/index.html and so on, below). A plain try_files $uri /index.html without $uri/ skips them and every crawler sees the home page's tags on every URL; with no fallback at all, a deep link returns 404.
  • /app/ must be a static directory holding the Android APK and latest.json (mobile/scripts/publish-apk.sh uploads there; see Mobile app). It must never be answered with the SPA shell: the service worker is told the same (navigateFallbackDenylist for /api/ and /app/).
  • Terminate TLS at the proxy; cookies are Secure in production and HSTS is sent for one year.

Build on the server

Because VITE_* are compiled in, a bundle built on a laptop carries the laptop's values. Build where the values live: put them in frontend/.env.production.local (git-ignored via *.local) on the host and run npm run build there. Build into a fresh directory and swap it in, keeping the previous one for rollback, so a failed build does not take the site down. The maintainers' own host follows this pattern: git pull in the checkout, build, swap frontend/dist, then pm2 restart mern-estate-api --update-env. Prefer a health probe that does not need a workspace (/api/health/live).

Health, readiness and shutdown

All answer before tenant resolution, so a broken tenant lookup cannot pull a pod out of service, and none are encrypted even when response encryption is on.

EndpointUseBehaviour
GET /api/health/liveLivenessAlways 200 { alive: true } while the process runs.
GET /api/health/readyReadiness200 when Mongo is connected and the process is not draining; otherwise 503. Includes redis: connected, degraded or not_configured, which never makes the instance unready.
GET /api/health/startupStartup (Render health check)200 { status: "ready" } once Mongo is connected, else 503 { status: "starting" }.
GET /api/health/healthSimple health (npm run health:check)Status, uptime, version, database status. No pid, Node version or heap sizes: the route is public.
GET /api/health/detailedOn-callDatabase latency, heap use (warns at 90%), whether SMTP and SMS are configured. 503 when degraded.
GET /api/health/metricsScraperMemory, CPU, database state. Bearer METRICS_TOKEN when set.

The reported version is read from the repository-root VERSION file (the same value for PM2, Docker and bare node). The Dockerfile copies it to /app/VERSION (the resolver looks one level above utils/), so the container reports it too; without the file the fallback is npm_package_version or 0.0.0-unknown.

Graceful shutdown

One ordered sequence in index.js; never add another SIGTERM handler. On SIGTERM/SIGINT (and after an unhandledRejection or uncaughtException, which exit with code 1): readiness flips to 503; the server stops accepting connections and idle keep-alives are closed; in-flight requests finish; the scheduler and cache listener stop; Socket.IO, Redis and Mongo close; logs are flushed; the process exits. After SHUTDOWN_TIMEOUT_MS (default 10 s) remaining connections are force-closed. Set the orchestrator's kill timeout longer than that.

Backups and restore

  • npm run db:backup (backend/scripts/backup.js) runs mongodump --gzip into $BACKUP_DIR/backup-<timestamp> (default <repo>/backups), prints the size, deletes a failed partial dump and keeps the newest BACKUP_RETENTION_COUNT (7). It needs MongoDB Database Tools on the host and MONGO_URI. Atlas has its own backups; this is for self-hosted or extra copies.
  • npm run db:restore -- --list shows what exists. Restore is destructive and has four safeguards: --confirm is required; it refuses in production unless ALLOW_PRODUCTION_RESTORE=true; on a terminal you must type the database name; and the target database name is printed first. It runs mongorestore --gzip --drop (use --no-drop to merge) and remaps the dump's database name onto the one in MONGO_URI. 
    npm run db:restore -- --list
npm run db:restore -- --from backup-2026-09-18T02-00-00 --confirm
  • node scripts/purgeWorkspaceData.js --workspace <slug> --confirm empties one workspace's working data but keeps the tenant, its admins and roles. It writes a JSON backup of what it is about to delete first and abandons the purge if that write fails; --dry-run and --keep-users exist.

The compose backup service runs mongodump --gzip and names directories backup-YYYY-MM-DDTHH-MM-SS, the same as backup.js, so db:restore can read them (point BACKUP_DIR at the volume). Dumps taken by an older compose file were not gzipped; restore those with mongorestore --drop directly. A dump is not a backup until it has been restored once.

Migrations and one-time scripts

All run from backend/. Scripts load models through scripts/_bootstrap.js (const { models, inWorkspace, close } = await bootstrapScript()), which registers the tenancy plugin first, takes --workspace <slug> and refuses to guess when several workspaces exist. Never import a model directly in a script: the records would have no tenantId and the app could never see them.

Index drift is a recurring trap: an obsolete index (an old non-partial phone_1) survives schema changes and blocks creating a second user without a phone number until it is dropped (or User.syncIndexes() is run once).

Logs and observability

  • utils/logger.js writes coloured lines to stdout and, when OPENOBSERVE_USERNAME/PASSWORD are set, buffers entries and ships them (every 3 seconds or 50 entries) to the streams backend_logs, security_logs, audit_logs, access_logs and frontend_logs. Every line carries the request id and tenant; flushLogs() runs at shutdown.
  • The browser posts client-side errors to POST /api/observability/logs (public, 120 per minute). Querying the store is POST /api/observability/query and GET /api/observability/streams, restricted to platform operators because the store holds every workspace.
  • Sentry is not wired. utils/sentry.js is a no-op stub kept so old imports resolve, and SENTRY_DSN is read by nothing. Observability goes to OpenObserve. A starter dashboard export is in openobserve-dashboard.json.
  • npm run logs:rotate renames logs/*.log with a date suffix and prunes by LOG_RETENTION_DAYS (default 30). PM2 writes its own files under logs/.
  • Per-request lines: one structured access entry in production (requestLogger); morgan('dev') only outside production.

Scheduled jobs

backend/jobs/scheduler.js is dependency-free and ticks every 60 seconds. Each run takes a lease in Mongo (models/jobLock.model.js), so N instances still fire a job once, and a slow run holds its lease instead of stacking. Job bodies run inside forEachTenant(). tick(now) takes the time as an argument; never read the clock inside cadence logic. Register jobs in jobs/index.js. Times are UTC.

JobCadenceDoes
task-reminders, followup-remindersevery 5 minReminder notifications.
webhook-deliveryevery 1 minDeliver queued webhooks.
sequence-stepsevery 15 minFire due email-sequence steps.
lead-rescoredaily 03:00Recompute scores (recency decays). Never touches won/lost leads; keeps manual temperature.
overdue-invoice-sweepdaily 07:30Flags billing.state; never suspends a workspace.
trial-expiry-sweepdaily 08:00Trial notices.

JOBS_ENABLED=false runs an instance that serves traffic but takes no leases, which is also what the CI end-to-end job sets. More on each job: Background jobs.

Scaling

  • Without REDIS_URL, the response cache and rate limiter are per process. Correct for one instance; on N instances caches diverge and every limit is N times looser. It is stated at boot rather than assumed.
  • With REDIS_URL: limits use a Redis store (key prefix rl:) and cache invalidation publishes to every instance. Call invalidateEverywhere({ prefix }) from utils/cache.js, not cache.clearByPrefix(). Redis being down degrades to per-process behaviour and does not fail readiness.
  • Scheduled jobs need nothing extra (Mongo leases). Socket.IO needs an adapter, which is not installed; the PM2 config therefore runs a single process (see above).
  • Uploads are on local disk (uploads/), so multiple hosts need a shared volume.

SEO build outputs

A single-page app ships one index.html, so a crawler that does not run JavaScript would see the home page's tags on every URL. frontend/seo/vite-plugin-seo.mjs runs at the end of vite build and writes into frontend/dist:

  • A real HTML file per public page, from the list in frontend/seo/pages.mjs: / (the built index.html, with the FAQ as JSON-LD), /download, /privacy, /terms, /cookies, /refunds. Each has its own title, description, canonical, Open Graph and Twitter tags, a WebPage JSON-LD block and a readable <noscript> fallback. React still boots on top.
  • sitemap.xml listing those pages with lastmod set to the build date, and robots.txt that allows /, disallows /api/, /uploads/, /app/, /s/, /invite/, /unsubscribe/, auth screens and the CRM routes, and points to the sitemap. There is no hand-written robots.txt.
  • All absolute URLs use VITE_SITE_URL (trailing slashes trimmed), defaulting to https://realvista.duckdns.org.
  • At runtime RouteSeo keeps the tags right after client-side navigation and serves noindex, nofollow for every route not in the list, so a forgotten route fails closed. The property book is not public, so a listing, search or CRM route must never become indexable by being omitted.

The web server needs the try_files fallback described above for these files to be served.

Release checklist

  1. CI green on the branch (backend and frontend lint/tests; read the advisory e2e and audit output).
  2. If you changed behaviour the public policies describe (cookies, retention, who receives data, export/delete), update frontend/src/pages/Legal.jsx in the same change and move LEGAL_UPDATED and LEGAL_VERSION together.
  3. If you changed a figure in tenancy/plans.js, remember it re-caps every live workspace on that plan. That is a commercial decision.
  4. Backup first: npm run db:backup (or confirm the compose backup ran), and know which dump you would restore.
  5. One-time migrations needed by this release? Run with --dry-run first, then for real.
  6. Production environment: all five required variables, FRONTEND_URL, APP_DOMAIN or DEFAULT_TENANT_SLUG, OpenObserve credentials, SMTP, REDIS_URL if more than one instance, distinct JWT secrets.
  7. Build the frontend on the host with the right VITE_* (including VITE_SITE_URL), into a fresh directory, then swap.
  8. Restart the API and wait for /api/health/ready to return 200; then check /api/health/detailed.
  9. Check a deep link such as /privacy returns its own HTML (view-source shows the Privacy title) and /sitemap.xml lists the right host.
  10. Smoke test: sign in, create a lead, open a share link, confirm a security-log line reached OpenObserve.
  11. Mobile release? Bump version: in mobile/pubspec.yaml and run mobile/scripts/publish-apk.sh (Mobile app).

Stale files and known drift

  • DEPLOYMENT.md (Render guide), AUDIT.md and similar top-level documents are marked superseded by this site but still describe Firebase storage and Sentry, both removed from the product. COMMANDS.md and DOCKER.md were corrected to Cloudinary. Uploads are Cloudinary; observability is OpenObserve.
  • backend/.env.example was cleaned to the variables the code reads, with the code's default rate limits (15 min window, 1000 / 20 / 30).
  • SMTP_FROM is the sender variable the code reads; the example and blueprint now say so, but the Deployment guide still says EMAIL_FROM.

One-time: drop the old user TTL index

Earlier builds declared a TTL index on refreshTokens.createdAt in the users collection. MongoDB applies a TTL on an array path to the whole document using the oldest element, so a user with one forgotten device could have been deleted 30 days after signing in there. The schema no longer declares it (backend/tests/userTtl.test.js guards that), but Mongoose does not drop indexes that already exist. On every deployment whose database was created before this change, drop it once:

// mongosh, against the app database
db.users.getIndexes().filter(i => i.expireAfterSeconds)      // confirm it is there
db.users.dropIndex('refreshTokens.createdAt_1')

If accounts have been disappearing about a month after their last sign-in on some device, restore them from a backup taken before they vanished (FAQ, npm run db:restore -- --list).
