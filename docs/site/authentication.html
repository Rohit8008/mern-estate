Authentication and sessions

How sign-in, cookies, refresh-token rotation, CSRF, lockout, password reset, invitations and operator "acting as" sessions work, and how the web app and the mobile app drive them.

The model in one minute

Authentication is cookie-only. There is no bearer-token mode: the API never reads an Authorization header for identity, and the browser never holds a token in script-reachable storage. A sign-in sets three cookies; every later request carries them automatically.

POST /api/auth/signin
→
access_token + refresh_token + csrf_token
→
401? POST /api/auth/refresh
→
rotated pair, retry once

The code lives in backend/controllers/auth.controller.js (issuing and rotating), backend/utils/verifyUser.js (verifyToken, tryVerifyToken, requireAdmin, requireRole), backend/middleware/csrf.js and backend/tenancy/resolveTenant.js.

Cookies

CookiehttpOnlyLifetimeWhat it is
access_tokenyesACCESS_TOKEN_EXPIRY (default 15m) plus a 1-minute bufferSigned JWT (JWT_SECRET). Proves the session.
refresh_tokenyesREFRESH_TOKEN_EXPIRY (default 30d)Signed JWT (REFRESH_SECRET). Only used to mint a new pair.
csrf_tokenno, on purpose30 days (fixed in middleware/csrf.js)Random 32-byte value, base64url. A proof of same-origin, not an identity.
  • Cookie lifetimes follow config. maxAge is derived from the same ACCESS_TOKEN_EXPIRY / REFRESH_TOKEN_EXPIRY that signs the JWT (durationToMs accepts s, m, h, d). A hard-coded 30-day cookie next to a 10-day token used to leave a stale cookie that outlived the token it carried and produced a confusing logout days later. The 1-minute buffer on the access cookie means the cookie always outlives its token.
  • SameSite and Secure. In production all three cookies are SameSite=None; Secure so the app can be served from a different origin than the API. In development they are SameSite=Lax and not Secure.
  • Clearing must match setting. A bare clearCookie('access_token') does not match a SameSite=None; Secure cookie, so the browser would keep it. clearSessionCookies() and the sign-out handlers clear each cookie with the same attributes it was set with.

These three are also the only cookies listed on the public Cookie Policy (pages/Legal.jsx); the names and the "about 15 minutes / 30 days" lifetimes there agree with the code.

JWT claims

Both tokens carry the same claims and differ only in secret and expiry. Issuer and audience default to mern-estate-api and mern-estate-client (JWT_ISSUER, JWT_AUDIENCE) and are verified on every request.

ClaimMeaning
idThe user's id.
tidThe workspace the account lives in. Signed, so it cannot be forged by changing a host or header. resolveTenant prefers it over everything else.
actOnly on a platform operator's token while viewing a customer's workspace: the workspace being viewed. Ignored unless pa is also true.
patrue only when startActingAs minted the token, after it re-read isPlatformAdmin from the database.
iat, exp, iss, audStandard. iat is compared with passwordChangedAt (see Passwords).

tid and act are never collapsed. Rewriting tid to the customer's workspace would put the operator's identity in a workspace their account is not in, and the session would stop resolving. Every query about the caller is pinned back to tid (inHomeTenant / runWithTenant); see Multi-tenancy.

Signing in

POST /api/auth/signin, rate limited (authRateLimit, 20 per 15 minutes per IP by default), body validated by userValidation.login.

curl -i -X POST http://localhost:3000/api/auth/signin \
  -H 'Content-Type: application/json' \
  -H 'x-tenant: acme' \
  -c cookies.txt \
  -d '{"email":"owner@acme.in","password":"Secret@123"}'

Success is 200 with the user document spread at the top level (no data wrapper; password and refreshTokens are removed), plus isPlatformAdmin so the console link can be shown to operators:

{ "success": true, "_id": "...", "email": "owner@acme.in", "role": "admin", "isPlatformAdmin": false, ... }

and three Set-Cookie headers (access_token, refresh_token, csrf_token). The server also bumps lastLogin and loginCount, resets the failure counters and writes a SecurityLog row.

Choosing the workspace

Every agency shares one server address, so a person signing in has no session, host or token to tell the server which agency they belong to. The sign-in screen has a Workspace field; its value travels as the x-tenant header (web: stored in localStorage under rv.workspace by frontend/src/utils/workspace.js; mobile: WorkspaceStore). resolveTenant resolves, most authoritative first:

  1. the tid claim on a valid access token;
  2. a custom domain;
  3. a single-label subdomain of APP_DOMAIN (reserved: www app api admin auth static cdn assets localhost);
  4. the x-tenant header;
  5. the default workspace (DEFAULT_TENANT_SLUG, default default).

Two rules keep this safe:

  • On entry routes the typed workspace beats an old cookie. POST /auth/signin, POST /user/password/request-otp, POST /user/password/reset and GET /tenant/lookup prefer the header over a session cookie left from another workspace. Otherwise signing in to B while holding A's cookie looked the email up in A and answered "invalid email or password".
  • A typo is an answer, not a fallback. A named workspace that does not exist returns 404 with code: "WORKSPACE_NOT_FOUND" instead of silently using the default, so nobody is signed in to another agency by mistake.
{ "success": false, "statusCode": 404, "code": "WORKSPACE_NOT_FOUND",
  "message": "There's no workspace called \"acmee\". Check the name and try again.",
  "requestId": "..." }

If a token names one workspace and the host names another, the request is refused (tenant_host_mismatch is logged): a valid session for one agency must not operate on another agency's domain. Suspended, cancelled or expired-trial workspaces answer 403 with a plain-language reason. GET /api/tenant/lookup (rate limited, public) lets the sign-in screen confirm a name and show the workspace's logo before the password is typed.

Failed attempts and lockout

  • Wrong email or wrong password both answer 401 "Invalid email or password", so the response does not say which half was wrong. The reason is recorded in the security log.
  • Each wrong password increments loginAttempts. At MAX_LOGIN_ATTEMPTS (default 5) the account gets lockedUntil = now + LOCKOUT_DURATION (milliseconds, default 900000, 15 minutes).
  • The lock check runs before the password check, so a locked account rejects even the correct password: "Account locked. Try again in N minute(s)."
  • A successful sign-in resets loginAttempts and clears lockedUntil.
  • Accounts with status inactive or suspended, and accounts with no password set, are refused with their own message (and, for disabled accounts, are also rejected by verifyToken on every later request without waiting for token expiry).

Lockout is per account, and the IP-based authRateLimit is separate: one slows a single account down, the other slows a single source down. With REDIS_URL unset the rate-limit counters are per process; see Deploy and operate.

Refresh and rotation

POST /api/auth/refresh reads the refresh_token cookie. It is a public write (the cookie is the credential), exempt from CSRF, and has its own higher limit (refreshRateLimit: max(AUTH_RATE_LIMIT_MAX x 5, 500) per window; the general API limiter skips this URL entirely).

  1. Verify the JWT with REFRESH_SECRET. Invalid: 401 "Invalid refresh token".
  2. Load the user in the home workspace (tid) and look for the SHA-256 hash of the presented token among the user's stored hashes.
  3. Not found = reuse. A well-signed token that is not on the list was already rotated away, so someone is replaying it. The server empties refreshTokens (every session of that user ends) and answers 401 "Invalid refresh token. Please log in again."
  4. Found: $pull the old hash, $push the new one, issue a new access and refresh pair and a new csrf_token.
  • Only hashes are stored. A database leak yields SHA-256 digests that are useless without the original tokens.
  • At most 10 concurrent sessions. Every push uses $slice: -10, so the 10 most recent are kept and the oldest device is signed out silently.
  • Atomic. $pull then $push avoids the read-modify-write race of splice-and-save.
  • Acting claims are re-checked. If the old token had pa: true and act, they are carried over only if the user is still isPlatformAdmin and active; otherwise they are dropped and acting_claim_dropped_on_refresh is logged. Revoking an operator ends their view into a customer's workspace at the next refresh.

Because a replayed token wipes all sessions, two tabs must never refresh independently with the same cookie. The web client serialises refreshes (below) and the mobile client does the same.

CSRF

Cookie-only auth plus SameSite=None in production means a cross-site form POST would carry the session. CORS does not help: a cross-origin application/x-www-form-urlencoded POST is a "simple request" with no preflight. So requireCsrfToken (mounted on all /api after tenant resolution) uses the double-submit pattern.

RequestResult
GET, HEAD, OPTIONSPasses.
A write on a route in security/publicRoutes.js (sign-in, refresh, password OTP/reset, invite accept, unsubscribe, contact form, log ingest)Passes: there is no ambient credential to forge. The exemption list is derived from the same allowlist the route-access test enforces, so the two cannot drift.
A write with neither access_token nor refresh_token cookiePasses to the route's own guard, which answers 401. Otherwise every signed-out write would report a confusing CSRF error.
Session cookies but no csrf_token cookie403 CSRF_COOKIE_MISSING: "Your session predates a security update. Please sign in again."
Cookie and X-CSRF-Token header differ (constant-time compare)403 CSRF_TOKEN_INVALID: "Please refresh the page and try again."

GET /api/auth/csrf returns { "success": true, "csrfToken": "..." }: the existing cookie value, or a fresh one (and cookie) if there is none. It exists for clients that cannot read cookies from script (a Flutter web build; a native app whose cookie jar is not script-visible). It is not a secret leak: same-origin script can read the cookie anyway, and a cross-origin page cannot read this response because CORS refuses it.

The token is rotated on sign-in, refresh, accept-invite, act-as and stop-acting, and cleared on sign-out. Clients must therefore read it at call time and never cache it for long; on CSRF_TOKEN_INVALID they re-fetch and retry once. CORS allows the header (allowedHeaders includes X-CSRF-Token and X-Request-Id); a cross-origin deployment whose preflight did not would reject every POST.

# Sign in, then write: the csrf_token cookie from sign-in is echoed as a header
CSRF=$(grep csrf_token cookies.txt | awk '{print $7}')
curl -X POST http://localhost:3000/api/clients \
  -b cookies.txt -H "X-CSRF-Token: $CSRF" -H 'x-tenant: acme' \
  -H 'Content-Type: application/json' -d '{"name":"Asha Verma","phone":"9876543210"}'

Signing out

  • POST /api/auth/signout (optional auth, tryVerifyToken): removes this refresh token's hash, clears all three cookies, logs the event.
  • POST /api/auth/signout-all (verifyToken): sets refreshTokens = [], so every device has to sign in again once its access token (at most 15 minutes) lapses.
  • There is no GET sign-out: it was removed because a GET can be triggered by <img src>.
  • POST /api/auth/signup exists only to answer 403 "Sign up is disabled. Contact admin." People join through invitations.

Both handlers pin their database writes to the caller's home workspace. During an acting session, an unpinned lookup finds nothing and the old code answered "signed out" while leaving the refresh token valid for 30 days; tests/actingAs.test.js covers this.

Passwords

  • Policy (validatePassword in middleware/security.js): at least 8 characters with an uppercase letter, a lowercase letter, a digit and one of !@#$%^&*(),.?":{}|<>. Enforced when accepting an invite, resetting and changing a password.
  • Storage: bcrypt (bcryptjs), cost 12, in the model's pre-save hook.
  • Tokens issued before a change are refused. A save that changes the password sets passwordChangedAt (one second in the past); verifyToken and tryVerifyToken reject any access token whose iat is earlier: "Session expired. Please log in again."

Password reset

Two public, rate-limited calls. Both honour x-tenant (they are entry routes).

POST /api/user/password/request-otp   { "email": "owner@acme.in" }
POST /api/user/password/reset         { "email": "owner@acme.in", "otp": "123456", "newPassword": "NewSecret@123" }
  • The request always answers 200 "If that address has an account, a code is on its way." with a masked address. The mail is deliberately not awaited, so a real address does not take an SMTP round-trip longer than an unknown one (the same leak, measured with a stopwatch).
  • The code is 6 digits, stored as a SHA-256 hash, valid for 10 minutes. After 5 wrong guesses (MAX_OTP_ATTEMPTS) it is destroyed.
  • Every failure on the reset call is the same 400: "That code is not valid or has expired."
  • Only outside production, and only when no SMTP is configured, the request response includes devOtp so the flow can be tested without a mail server. Never for an address with no account.
  • A signed-in user changes their own password with POST /api/user/password/change (currentPassword, newPassword; the new one must differ). Every other device is signed out; the calling device stays signed in on a fresh token pair.

The reset, the self-change and an admin setting an employee's password (/api/user/admin/set-employee-password/:id) all clear the user's stored refresh tokens, and /refresh rejects a refresh token issued before passwordChangedAt (401, and the stored list is emptied). Use signout-all to end sessions without changing the password.

Invitations

An invitation is how anyone first gets into a workspace, including a brand-new agency's first admin. The recipient has no session and does not know "workspace" is a concept, so the token carries it.

  • Token: 32 random bytes, base64url; only its SHA-256 hash is stored (tenancy/invites.js). It expires after 7 days by default (DEFAULT_INVITE_DAYS) and is single-use.
  • GET /api/auth/invite/:token returns data: { email, name, hasPassword, workspace: { name, slug, logoUrl, tokens } } so the page can be branded and remember the workspace. Nothing else about the user.
  • POST /api/auth/invite/:token takes { "password": "...", "acceptTerms": true }. It applies the password policy, requires acceptTerms === true, stores legalAcceptance = { version: LEGAL_VERSION, acceptedAt }, activates the account, consumes the token and signs the person in with a session whose tid comes from the user record, not from anything the caller sent.
  • Both are rate limited and CSRF-exempt (the token is the credential).
  • Unknown, expired and used tokens look identical (404 "This invitation is no longer valid. Ask for a new one."), so the endpoint is not an oracle for outstanding invitations.
  • Re-sent invitations. Sending again replaces the hash, and up to the 4 previous hashes are remembered. Opening an older link while a newer one is still valid answers 410 with code: "INVITE_REPLACED" and "A newer invitation was sent to you." That tells the invitee to open the newer email and tells a guesser nothing, because only someone holding a once-valid link can reach it.

Operator "acting as" sessions

A platform operator (isPlatformAdmin, a flag on the User that is select: false and never settable through a tenant-facing API) can view a customer's workspace to answer "what does the customer actually see?".

  • POST /api/platform/act-as/:id re-issues the session with act: <target>, pa: true, rotates the refresh token, logs acting_as_started and answers { actingAs: {...}, readOnly: true }. POST /api/platform/stop-acting issues an ordinary pair again.
  • resolveTenant scopes the request to act; the user lookup stays on tid. A suspended or expired workspace can still be opened, since that is exactly when support needs to.
  • Read-only at the edge. tenancy/readOnlyWhileActing.js blocks every non-GET with 403 "You are viewing <name> as a platform operator. This view is read-only..." and logs acting_write_blocked. Exempt: POST /api/platform/stop-acting, /api/platform/act-as, /api/auth/signout, /api/auth/signout-all, /api/auth/refresh, /api/user/legal-acceptance (the last writes to the operator's own record in their home workspace). Paths with ./.. segments, empty segments or encoded slashes are refused rather than interpreted.

What every protected request goes through

  1. Request id, security headers, body parsing, rate limit (general limiter keyed by user id from the access cookie, else IP).
  2. resolveTenant sets the tenant context.
  3. readOnlyWhileActing, then requireCsrfToken.
  4. The route's guard: verifyToken verifies the JWT (issuer, audience), loads the user in tid, rejects inactive/suspended accounts and tokens older than passwordChangedAt, then sets req.user (id, email, username, status, role, assignedCategories, assignedRole). An employee with no role is assigned the system "Employee" role on the fly.
  5. requireAdmin / requireRole(...) / requirePermission(key) (see Team, roles and permissions).

Failures return the standard error envelope (API conventions). 401 means "no usable session"; 403 means "signed in but not allowed".

Web client behaviour

frontend/src/utils/http.js is the only place that talks to the API; call sites use apiClient (get, post, put, patch, delete, upload), never raw fetch.

  • Every call goes through fetchWithRefresh: credentials: 'include', X-CSRF-Token read from the csrf_token cookie at call time for non-safe methods, and x-tenant from the stored workspace.
  • On a 401 it calls refreshAccessToken() once. Concurrent 401s share one in-flight refresh promise. If it succeeds the original request is retried once, with the CSRF header re-read because the refresh just rotated it.
  • If the refresh fails and the page is not /sign-in, a window event auth-error is dispatched and the app returns to sign-in. Errors raised by apiClient carry code, details and requestId; handleApiResponse also fires an api-error event (a toast) unless the call passed silent: true.
  • setUserSignedOut(true) is called before a deliberate sign-out so in-flight 401s do not trigger a refresh that would resurrect the session; false after the next sign-in.
  • When response encryption is on, the same module decrypts transparently (API conventions).

Sockets authenticate once, at the handshake: backend/socket.js reads access_token from the Cookie header, verifies it, requires a tid claim ("Session predates workspaces. Please sign in again." otherwise) and rejects disabled accounts. Each connection joins user:<id> and tenant:<tenantId> rooms.

Mobile client

The Flutter app (mobile/lib/core/network/api_client.dart) uses the same cookie protocol: Dio with a disk-persisted PersistCookieJar so the session survives restarts, an x-tenant interceptor fed by WorkspaceStore, a refresh-on-401 interceptor (not applied to signin/refresh/signup, one retry, concurrent 401s deduplicated), and a CSRF interceptor that calls GET /api/auth/csrf instead of reading a cookie and retries once on CSRF_TOKEN_INVALID. For Socket.IO on native it copies the jar's cookies into an explicit Cookie header. See Mobile app.

Security log

Sign-in success and failure (with reason), refresh success and reuse, and sign-out are written to the SecurityLog collection (email, method, status, reason, IP, user agent, path) and mirrored to the OpenObserve security_logs stream. Rows expire after 180 days via a TTL index. See Security.
