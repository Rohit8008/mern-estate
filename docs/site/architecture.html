System architecture

How the monorepo, the Express API, the models, realtime, caches, search and notifications fit together, and the rules that keep them safe.

The shape of the system

The repository is one monorepo with a Node/Express API, a React single-page app and a Flutter mobile app. One deployment serves many agencies (tenants) from a single MongoDB database. Everything else on this page follows from that decision, so read Multi-tenancy and platform admin alongside it.

The exact order, and why it matters, is in Request pipeline and errors. The short version: everything after resolveTenant runs inside an AsyncLocalStorage tenant context, so every Mongoose query is filtered by tenantId without any controller asking for it.

Startup sequence (backend/index.js)

  1. Register tenancy first. registerTenancy(mongoose) installs the global tenant plugin. A Mongoose global plugin only applies to schemas compiled after it is registered, and ES imports are hoisted, so index.js deliberately uses await import('./server.js') after registering. Importing any model before this line would produce a model with no tenantId.
  2. validateConfig() checks secrets and production settings (see Configuration) and exits on error.
  3. registerBuiltinRules() fills the workspace rule vocabulary, because rules are resolved by name and must exist before the first request can run a hook.
  4. startCacheInvalidationListener() subscribes to Redis when REDIS_URL is set; otherwise it is a no-op.
  5. setupSocket() attaches the Socket.IO connection handlers, then startServer() connects to Mongo, seeds default property types for any workspace that has none, and listens.
  6. startJobs() runs after the server is listening, so a job failure cannot stop boot. JOBS_ENABLED=false skips it (see Background jobs).

Shutdown sequence

There is exactly one shutdown path, shutdown(reason, exitCode) in index.js, bound to SIGTERM, SIGINT, unhandledRejection and uncaughtException. Never add another SIGTERM handler. The pieces used to race: the database module exited the instant Mongo disconnected, so in-flight requests got a reset connection, the logger's flush lost, and the scheduler's lease was never released.

  1. markShuttingDown() (utils/lifecycle.js) makes GET /api/health/ready answer 503 so a load balancer stops sending traffic.
  2. Stop accepting connections and wait for in-flight requests (server.close, plus closeIdleConnections so keep-alive sockets do not hold it open).
  3. stopScheduler() and stopCacheInvalidationListener().
  4. Close Socket.IO, Redis, and the Mongo connection.
  5. flushLogs(), then process.exit.

SHUTDOWN_TIMEOUT_MS (default 10000) bounds the wait; after it, remaining connections are closed forcibly.

backend/ecosystem.config.js sets PM2 kill_timeout: 5000, shorter than the 10 s default drain, and wait_ready: true although nothing in the backend calls process.send('ready') (PM2 then falls back to listen_timeout). If you rely on PM2 for graceful drains, raise kill_timeout above SHUTDOWN_TIMEOUT_MS.

Configuration

backend/config/environment.js loads backend/.env and exits immediately if any of these are missing: JWT_SECRET, REFRESH_SECRET, MONGO_URI, NODE_ENV, MESSAGE_ENCRYPTION_KEY. The last one is required because without it the first Socket.IO message send would throw inside an unhandled-rejection handler and take the server down.

Models

There are 36 Mongoose models in backend/models/. All are tenant-scoped except three that describe the platform itself (tenantScoped: false): Tenant, Invoice and JobLock.

AreaModels

People and accessUser, Role, SecurityLog

CRMClient (leads; deals are embedded), Owner, BuyerRequirement, LeadSource, Task, CalendarEvent, Transaction
AutomationSequence, SequenceEnrollment, Webhook, WebhookDelivery, EmailTemplate, EmailSuppression
ReportingReportTemplate, GeneratedReport, ActivityLog, ImportUsage

Uniqueness is always per workspace: indexes are written as { tenantId: 1, field: 1 }, { unique: true }, never a bare unique: true (a global unique would let whichever agency signed up first claim a slug or name). The exceptions are the global collections, e.g. Invoice.number and JobLock.name. Category is the live category system the UI uses; PropertyType is a parallel older system that is still seeded per workspace at boot.

Controller, route and validation conventions

  • One router file per mount point in routes/*.route.js, mounted in app.js under /api/<name> (for example /api/listing, /api/clients, /api/webhooks).
  • Handlers are wrapped in asyncHandler (utils/error.js) so a rejected promise reaches globalErrorHandler. Throw AppError or one of its subclasses (ValidationError, NotFoundError, ConflictError, VersionConflictError...) instead of hand-writing error JSON.
  • Every POST/PUT/PATCH has validateBody(schema) (Joi, stripUnknown: true). A structural test fails the build on a write route without one.
  • Guards: verifyToken for a session, requireAdmin for workspace admins, requirePermission('key') for catalogued permissions, requirePlatformAdmin for the vendor console. Every mounted route must be guarded or listed in security/publicRoutes.js.
  • Lists take page, limit and sort=key:asc|desc through utils/listQuery.js.
  • Success responses use sendSuccessResponse(res, data, message) which returns { success: true, statusCode, message, data, timestamp }; some older handlers write their own { success: true, ... } shapes.

All of this is covered in detail on Request pipeline and errors.

Realtime (Socket.IO)

backend/socket.js creates the server; backend/server.js registers the handlers.

  • Auth at the handshake. The access_token cookie is verified (issuer and audience included). A token without a tid claim is refused ("Session predates workspaces"). The user is looked up inside the token's workspace and disabled accounts are rejected. The socket stores socket.userId and socket.tenantId.
  • Two rooms per connection: user:<userId> for one person and tenant:<tenantId> for the workspace. A bare io.emit() reaches every socket on the deployment, which in a shared database means every other agency. Use emitToTenant(tenantId, event, payload) or emitToUser(userId, event, payload) from socket.js; io.emit( should not appear outside that file.
  • A socket is not a request, so nothing sets up a tenant context for it. Each handler wraps its database work in runWithTenant({ tenantId: socket.tenantId, userId }, fn).
  • Events: server-to-client presence:update, presence:bulk, unread:messages, message:new, conversations:update, typing, stop_typing, notification:new; client-to-server message:send (with an ack callback), typing, stop_typing.
  • Presence is per workspace (utils/onlineUsers.js, keyed by tenant). It used to send the process-global set, handing each connection every signed-in user id on the platform.
  • Messages are encrypted at rest with MESSAGE_ENCRYPTION_KEY (utils/encryption.js), rate limited to 30 per minute per user in process memory, and the recipient is looked up inside the sender's workspace, so an id from another agency simply is not found.

Uploads and files

  • Images and voice notes go to Cloudinary directly from the browser (frontend/src/utils/cloudinary.js, unsigned upload preset; audio and video use Cloudinary's video resource type). It needs VITE_CLOUDINARY_CLOUD_NAME and VITE_CLOUDINARY_UPLOAD_PRESET. CSP connectSrc allows api.cloudinary.com and res.cloudinary.com.
  • The backend still has POST /api/upload/single|multiple|audio (routes/upload.route.js): multer in memory (10 MB images, 25 MB audio), magic-byte validation through utils/fileValidation.js, then written to backend/uploads/ under a server-chosen name. Only listing photographs and avatars are served from /uploads; they are referenced by <img> on share pages that have no session. These routes are covered by the strict rate limiter and the plan's storage cap.
  • Documents are never public. Contracts, RERA certificates and layout plans go through /api/documents and are served by /api/documents/file/:name after authentication and an ownership check. /uploads/docs/* (old absolute URLs) redirects with 307 to that route rather than serving a file.
  • Use normalizeImageUrl() from @/utils/http for every image URL; it converts absolute localhost URLs to relative paths.

Caches

All response caching is in-process (utils/cache.js): a MemoryCache with a TTL and a simple LRU eviction by insertion order.

APIUse for
getTenantScopedCache(opts)Anything derived from one workspace's data (listing search, category and property type lists). Keys get a ::t=<tenantId> suffix automatically.
getCache(opts)Genuinely global data only (for example geocoding). A deliberate choice every time.
invalidateEverywhere({ prefix | key | all })Any write that invalidates a cached read. Clears locally and publishes to Redis so every instance drops the same keys.

A response cache sits in front of the database, so Mongoose query scoping cannot protect it. Before getTenantScopedCache existed, /api/listing/search and /api/category/list cached under keys like category:list: the query ran correctly for tenant A, and tenant B was then served A's data without a query running. The tenant goes in a suffix so existing clearByPrefix('listing:') invalidation still matches across tenants.

  • Cached reads stay local (a local Map beats a network round trip, and the TTL bounds staleness). Only invalidation is shared: invalidateEverywhere publishes {from, prefix, key, all} on the Redis channel cache:invalidate; each instance ignores messages it sent itself.
  • Without REDIS_URL this is a no-op and behaviour is exactly per-process. On a PM2 cluster or multi-dyno setup, an edit on instance A without Redis leaves B serving the old value until its TTL expires, which shows up as an edit that "sometimes doesn't save".
  • Caveat: getCache() is a singleton, so the TTL and size passed by the first caller win for the shared instance.
  • Two other caches are deliberately separate instances: the tenant record cache in resolveTenant.js (60 s TTL, 500 entries, so a busy list request cannot evict tenants) and the role cache in middleware/permissions.js (60 s, 200 entries). Neither is shared across instances, so a role or suspension change can take up to a minute to reach every instance.

Redis (optional)

utils/redis.js returns a shared ioredis client only when REDIS_URL is set and never throws: if Redis is unreachable the app degrades to per-process behaviour rather than failing. With Redis the rate limiter uses a RedisStore (key prefix rl:) so a "20 attempts per 15 minutes" limit really is 20, not 20 times the number of instances. GET /api/health/ready reports redis as connected, degraded or not_configured but never turns the instance unready over it.

Listing search

backend/search/listingSearch.js is the only listing search. The properties board (GET /api/listing/search), the global search and the command palette all delegate to it. Do not add a fourth path.

Matching is tiered and stops as soon as there are enough results (ENOUGH = 5):

  1. identifier - property number, pincode or id, exact.
  2. text - MongoDB $text, ranked by textScore.
  3. prefix - anchored ^term on city, locality, area name and name. Anchored so it can use an index; it answers half-typed words that $text (whole words only) cannot.
  4. fuzzy - an unanchored regex built by buildFuzzyRegex, last resort, only over a set the filters already narrowed.

Ranking and paging happen in the database with $facet returning both the page (rows) and a true total from one pass, so a count always describes exactly the rows returned. The previous implementation pulled 500 rows into Node, scored them there and sliced, so total was the size of that truncated pull and page 42 could be empty while matches existed.

GET /api/listing/facets (getListingFacets) returns counts per status, category, city, locality, type and assigned agent (each capped to the top 50 values) over the whole filtered set, plus totals (count, total value, average price ignoring zero placeholder prices). Use it for any header count; never count a page. Counts and rows share buildListingFilter, so they cannot be computed from different filters.

The $text-first trap. MongoDB requires $text to be in the first $match of a pipeline. The tenant plugin therefore merges tenantId into a leading $match instead of unshifting a second one (which would push the caller's $text to stage two and fail with "$match with $text is only allowed as the first pipeline stage"). If you change how the plugin handles aggregations, keep that property. The plugin also casts the id to an ObjectId explicitly, because aggregation pipelines are not cast against the schema: a string id silently matches nothing, which reads as "this tenant has no data".

Notifications

utils/notify.js is the one entry point for telling a person something. notify({ to, type, title, body, link, entity, actorId, email }):

  1. Validates type against utils/notificationTypes.js (unknown types are logged and ignored).
  2. De-duplicates recipients and drops the actor, so nobody is notified of their own action.
  3. Loads active users and resolves each one's saved preferences. In-app always happens unless the user turned it off; email defaults per type (defaultEmail).
  4. Writes a Notification row and pushes notification:new to the user's socket room.
  5. Sends mail through sendMail, using the workspace's own template for that event if it has written one.

It never throws: a notification is a side effect and failing to tell someone must not fail the request. Do not call sendMail from a controller for an event a person should see. That is how task mail once went to a single global NOTIFY_TO address instead of the assignee. workspaceAdminIds() returns the admins to address for workspace-level events (plan limits, trials). The types are listed in Background jobs and automation.

Outbound mail (utils/mailer.js) uses the workspace's own SMTP settings if tenant.mail.enabled; the password is stored AES-GCM encrypted and is select: false. Otherwise it falls back to the platform transport. SMTP timeouts are 8 s connect, 8 s greeting, 10 s socket, so a dead mail server costs a request a "could not send", not a hang.

Printing

There is no server-side PDF generation (no headless Chrome). The convention is four CSS classes in frontend/src/index.css inside @media print: .print-area (when present, only this subtree prints), .no-print, .print-only (hidden on screen, shown on paper) and .print-stack. Use <PrintButton /> (components/PrintButton.jsx), which calls window.print(); browsers already offer "Save as PDF" from their own dialogue.

Workspace rules and webhooks

Per-workspace behaviour that goes beyond settings is a named rule from a fixed vocabulary in code, selected by config; config never carries code. Outbound webhooks let an agency wire the CRM to Zapier, Make or n8n. Both are explained in Background jobs and automation.
