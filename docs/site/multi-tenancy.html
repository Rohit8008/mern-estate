Multi-tenancy and platform admin

One database, many agencies - how queries are scoped by a global Mongoose plugin, how a request picks its workspace, and how the vendor console, act-as, plans and billing sit on top.

The model: shared database, one tenantId per document

A tenant (also called a workspace) is one real-estate agency. All tenants share one MongoDB database; every document carries a tenantId. Isolation is enforced by code rather than by the database, so the code is written to fail loudly rather than quietly do the wrong thing.

  • Never build a tenantId filter by hand. A global Mongoose plugin (backend/tenancy/tenantPlugin.js) adds it to every query, aggregation and write.
  • Never add a bare unique: true. Uniqueness is per workspace: schema.index({ tenantId: 1, field: 1 }, { unique: true }). A global unique lets whichever agency signed up first claim a slug or name for everyone.
  • A query with no tenant context throws (TenantScopeError). This is deliberate; see the tenant context.
  • Only three collections are global (tenantScoped: false in their schema options): Tenant, Invoice and JobLock.

The tenant plugin

registerTenancy(mongoose) is called at the top of backend/index.js (and of every script, via scripts/_bootstrap.js) before any model is imported. It also sets applyPluginsToChildSchemas to false: otherwise every embedded subdocument schema (voice notes on a listing, deals on a client, field definitions on a category) would get its own required tenantId and every write would fail with "branding.tenantId is required".

What the plugin does to each schema:

OperationBehaviour
find, findOne, count, countDocuments, distinct, update*, delete*, findOneAnd*, replaceOneInjects tenantId into the filter. If the filter already names a different tenant, it throws instead of overriding.
upsertsStamps tenantId with $setOnInsert, so a matched document never has its tenant rewritten.
aggregatePuts the $match at the very front, before any $lookup or $group can widen it. Merges into a leading $match rather than unshifting (needed for $text, see listing search) and casts the id to an ObjectId, since pipelines are not cast.
save / createStamps tenantId in a pre('validate') hook (validation runs as its own pre-save hook registered earlier, so stamping on save would be too late and every create would fail with "tenantId is required"). tenantId is immutable: a record never moves between agencies by accident.
insertManyStamps a copy of each element. Callers pass module-level constants (seed data, starter roles); mutating those made the first insert poison every later one with a stale tenant id.
bulkWriteMongoose fires no query middleware for it, so the plugin overrides the static and scopes each operation by hand. This is the fast path bulk import uses.
estimatedDocumentCountThrows. It reads collection metadata with no filter, so it would report every tenant's rows. Use countDocuments().

A deliberate cross-tenant read on a model can also be written Model.acrossTenants('reason').find(), which requires a reason string.

The tenant context

backend/tenancy/tenantContext.js keeps the current tenant in Node's AsyncLocalStorage. The value is bound to one request's async chain, so two concurrent requests for two agencies cannot see each other's context (a module-level variable would not guarantee that).

FunctionUse
runWithTenant({ tenantId, tenant?, userId? }, fn)Run fn inside one workspace. Throws if given neither a tenantId nor an explicit bypass.
withTenantBySlug(slug, fn) (resolveTenant.js)Same, looking the workspace up by slug. For scripts and non-request work.
forEachTenant(fn, { serviceableOnly = true }) (tenantContext.js)Run fn(tenant) once in every workspace. One workspace failing does not stop the others (failures are collected). Skips suspended, cancelled and expired-trial workspaces unless serviceableOnly: false. This is what scheduled jobs use.
runWithoutTenantScope('why', fn)Deliberately unscoped work: the platform console, migrations, the login lookup that must find a user before it knows the tenant. The reason string is mandatory and is recorded on the context so an audit can ask "which code paths run unscoped?".
inHomeTenant(req, fn)Pin a lookup about the caller to their home workspace. See act-as.
getTenantId(), getTenant()Read the active context (null when unscoped).

runWithTenant forces the callback's thenable to start executing while the context is still bound. A Mongoose query is lazy: await runWithTenant(store, () => Model.find()) would otherwise create the query inside the scope but execute it outside it, with no context at all.

forEachTenant exists twice with different signatures. tenancy/tenantContext.js exports forEachTenant(fn, opts), which the scheduler jobs use. tenancy/resolveTenant.js exports forEachTenant(reason, fn), which iterates only trial and active workspaces and is used by server.js to seed default property types. Check the import path before using one.

How a request picks its workspace

resolveTenant() (backend/tenancy/resolveTenant.js) is mounted on /api after health and unsubscribe. It decides the tenant, then runs the rest of the request inside that tenant's context. Order, most authoritative first:

  1. The tid claim on the signed access_token cookie. Cannot be forged.
  2. A custom domain (tenant.customDomain, e.g. crm.acme.in).
  3. A subdomain of APP_DOMAIN (acme.<APP_DOMAIN>). Only a single label counts (a.b.<domain> is not tenant "a.b"), and these are reserved and never treated as tenants: www app api admin auth static cdn assets localhost.
  4. The x-tenant header, a workspace slug. This is what the sign-in screen's Workspace field (web and mobile) and API clients send.
  5. The default tenant (DEFAULT_TENANT_SLUG, default default): single-workspace deployments, and the migration window before every session carried a tenant claim.

Rules that follow from real bugs or abuse cases:

  • Token and host must agree. If the token names one tenant and the host names another, the request is refused with a security log entry (tenant_host_mismatch). A valid session for one agency must not operate on another agency's domain.
  • A named workspace that does not exist is an answer, not a reason to fall through. An unknown x-tenant slug yields 404 with code WORKSPACE_NOT_FOUND; a typo on the sign-in screen must never sign someone in to the default agency.
  • On entry routes the typed workspace wins over a leftover cookie. POST /auth/signin, POST /user/password/request-otp, POST /user/password/reset and GET /tenant/lookup prefer the header over the session cookie. Otherwise signing in to workspace B while holding A's cookie looked the email up in A and answered "invalid email or password".
  • Not serviceable means 403. A suspended or cancelled workspace, or a trial past trialEndsAt, gets a message to contact support. (Exception: an operator acting-as can still open it. See below.)
  • Tenant records are cached 60 s in process (negative results too, so a flood of requests for a non-existent subdomain is not a flood of queries). Suspending a workspace therefore takes effect within about a minute on every instance without a deploy.

In production, validateConfig() refuses to boot unless APP_DOMAIN or DEFAULT_TENANT_SLUG is set. Without either, requests fall back to a workspace called default that may not exist, and since a query with no tenant throws, the whole API would be down rather than degraded.

Platform admin versus workspace admin

There are two kinds of administrator, and confusing them would be the worst bug in the product.

Workspace adminPlatform admin (operator)
Flagrole: 'admin' on UserisPlatformAdmin: true on User (select: false)
ScopeAdministers ONE agency. There is one per tenant, eventually hundreds.The vendor's staff; administers every workspace.
GuardsrequireAdmin, requirePermissionrequirePlatformAdmin (middleware/platformAuth.js) on /api/platform/*
Can change plan/limits/status?No. PLATFORM_ONLY in tenant.controller.js lists slug customDomain status plan features limits trialEndsAt internalNotes; an attempt is rejected, not silently dropped.Yes.

role: 'admin' is not sufficient for anything under /api/platform: if it were, every customer's own admin could provision workspaces and read across the estate. requirePlatformAdmin re-reads the flag from the database on every call (it is deliberately absent from req.user) and requires status: 'active'. A denied attempt is logged at security level (platform_access_denied). The flag must never be settable through a tenant-facing API; the data-rights erase endpoint also refuses to erase an operator.

The platform API (routes/platform.route.js): GET /api/platform/summary, /tenants, /tenants/:id, /tenants/check-slug, /plans, /tenants/:id/billing; POST /tenants, /tenants/:id/suspend, /resume, /invite, /plan, /invoices, /invoices/:invoiceId/pay and /void, /act-as/:id, /stop-acting; PATCH /tenants/:id. See the generated reference.

Provisioning a workspace

provisionTenant() (backend/tenancy/provisionTenant.js) is the single function used by both the platform API (POST /api/platform/tenants) and the CLI (backend/scripts/provisionTenant.js), so a workspace made by a script is identical to one made in the console. A Tenant row alone is not a usable workspace: without roles there is no permission model, without an admin nobody can sign in, without a category the property form has nothing to offer.

  1. Tenant - slug normalised and validated (3-40 chars of lowercase letters, digits and hyphens; a reserved list such as www, api, admin, platform, billing, demo is refused; must be free). plan defaults to trial, with a 14-day trialEndsAt (trialDays). Any other plan starts active. Limits come from the plan.
  2. Starter roles - Super Admin, Employee, Viewer (STARTER_ROLES), deep-cloned per workspace.
  3. First admin - role: 'admin', assigned the Super Admin role. With no adminPassword the account is created with an invitation token and an invite email is attempted; the raw link is returned once so the operator can pass it on if mail fails. A password chosen by the vendor and emailed around is a password everyone keeps using.
  4. A starter category ("Residential Plots") unless seedSampleData: false.

There is no transaction (they need a replica set, and single-node deployments cannot start one), so it compensates: it records what it created and deletes it in reverse order if a later step throws, deleting rather than soft-deleting so the slug is not held hostage on retry. That is weaker than a transaction under a hard crash; if the database moves to a replica set, wrapping it in a session is a small change.

# From /backend. The first run needs --platform-admin: the very first operator
# cannot be created through an API that requires an operator.
node scripts/provisionTenant.js --name "Acme Realty" --slug acme \
     --admin-email owner@acme.in [--admin-password '...'] \
     [--plan growth] [--trial-days 30] [--no-sample-data] [--platform-admin]

Acting as a customer: identity is pinned, data is not

A platform operator can view a customer's workspace to answer "what does the customer actually see?". The mechanics have two halves that must never be collapsed.

JWT claimMeaning
tidThe workspace where the operator's account lives. Always their home workspace.
actThe workspace they are currently viewing.
paA signed true that proves the token was minted for an operator. act is honoured only alongside pa.
POST /api/platform/act-as/:id
→
requirePlatformAdmin re-reads isPlatformAdmin
→
reissueSession: tid = home, act = target, pa = true
→
resolveTenant scopes request to act
→
non-GET blocked at the edge
  • startActingAs is the only place that sets pa, after requirePlatformAdmin re-read the flag from the database. It replaces the refresh token in the same call and logs acting_as_started (operator email, home and target workspace, IP). POST /api/platform/stop-acting reissues a plain session and logs acting_as_ended.
  • A token carrying act without pa is simply scoped to the user's own workspace.
  • Refresh re-checks the privilege. On POST /api/auth/refresh the act and pa claims are only carried forward if isPlatformAdmin is still true and the account is active; otherwise they are dropped and logged (acting_claim_dropped_on_refresh), so revoking someone's platform access ends their view into a customer at the next refresh.
  • If the target workspace was deleted while the operator was inside it, resolution falls back to their home workspace (the safe direction to fail). The acting target is not gated on isServiceable(): a suspended or expired workspace is exactly the one support needs to open.
  • req.homeTenant / req.homeTenantId hold the operator's own workspace; req.tenant / req.tenantId hold the viewed one; req.actingAs carries the target's name, slug and status. GET /api/tenant/config exposes actingAs so the shell can show a banner (ActingAsBanner.jsx) and a way out, and its ETag includes act/own so a cached response cannot survive a switch.

Every query about the caller must be pinned

resolveTenant scopes the request to act, but the operator's user record, roles, permissions and refresh tokens live at home. So any query about the CALLER (User.findById(req.user.id), User.findByIdAndUpdate(req.user.id, ...), a SecurityLog write about a session) must run through inHomeTenant(req, fn). It is a no-op when nobody is acting. The failure mode is silent: an unpinned lookup runs in the customer's workspace, finds nothing, and nothing reads as "signed out" or as "nothing to do". Real bugs from exactly this:

  • tryVerifyToken (optional auth) failed silently, so signOut skipped its if (req.user) block and answered "signed out" while leaving the refresh token valid for 30 days.
  • Auth security logs wrote the operator's email into the customer's securitylogs.
  • Unpinned, the "assign the default Employee role" fix-up in verifyToken would have written the customer's Role id onto the operator's account, silently stripping their permissions at home.

verifyToken and tryVerifyToken look the user up with runWithTenant({ tenantId: payload.tid }). requirePlatformAdmin uses req.homeTenantId. tests/actingAs.test.js covers all of this.

The acting session is read-only

tenancy/readOnlyWhileActing.js is mounted once on /api, so a controller added later inherits it. While req.actingAs is set, every non-GET/HEAD/OPTIONS request is rejected with a 403 (AuthorizationError, and a acting_write_blocked security log) unless it is one of five session-level writes:

POST /api/platform/stop-acting
POST /api/platform/act-as          (prefix match - carries an id)
POST /api/auth/signout
POST /api/auth/signout-all
POST /api/auth/refresh
POST /api/user/legal-acceptance    (written via inHomeTenant, so it lands on the operator's own record)

If you exempt anything else, check that it does not write into the customer's workspace. The alternative (allow writes, log loudly) was rejected: an operator who can silently edit customer data is a liability the customer cannot audit, and an agency's audit trail should name a person at that agency. The prefix match is defensive about ambiguity: a . or .. segment, an empty segment, an encoded slash or malformed encoding refuses outright.

Plans and limits

backend/tenancy/plans.js is the single source for what a plan includes. Prices are in the smallest currency unit (paise), per month; null means "talk to us". A limit of 0 means unlimited.

PlanMonthly price (INR)maxUsersmaxListingsmaxStorageMbmaxImportRowsPerMonth
trial0 (14 days)32505122000
starter249900 paise (2,499)102500204820000
growth749900 paise (7,499)402500010240100000
enterprisenegotiated0000

Changing a figure in PLANS re-caps every live workspace on that plan the next time the plan is applied. That is a commercial decision, not a refactor. provisionTenant.js re-exports limitsForPlan and a deprecated PLAN_LIMITS from plans.js. Note that the schema default in tenant.model.js (limits: 25 users, 10000 listings, 5120 MB, 50000 rows) matches no plan; every provisioned workspace overwrites it from its plan.

  • applyPlan(tenantId, plan, { keepOverrides = true }) (tenancy/billing.js) moves a workspace's limits with its plan. A cap an operator set by hand survives: only values that differ from the old plan's figure count as deliberate overrides, so "the same as the plan" does not pin itself forever. Moving to a non-trial plan sets billing.state from none/trialing to active and ends the trial (status becomes active).
  • Limits gate creation, never reads (tenancy/limits.js). A workspace over its cap after a downgrade keeps full access to what it has; locking an agency out of its own property register over a billing question is never the right response. Exceeding a cap answers 402 (PlanLimitError, error code PLAN_LIMIT) rather than 403: "your plan doesn't cover this", not "you may not". The message says what to do next.
  • assertWithinLimit(key, countFn, adding) is called by creators (users, listings). The count function only runs if a cap exists, so unlimited plans cost no query. assertStorageAvailable(bytes, usedBytesFn) weighs uploads in whole MB, rounded up; usage is measured from the Document collection only (images and voice notes leave no size record).
  • The monthly import allowance is a meter, not a count. reserveImportRows(rows) atomically increments a per-workspace, per-month counter in ImportUsage ({tenantId, month} unique, month is "YYYY-MM" in the workspace's own timezone). The update only matches while the counter has room; when it does not, the upsert collides with the unique index and that collision is the refusal. It returns a release(unused) to hand back rows that did not land. See imports.
  • GET /api/tenant/usage shows used versus cap per limit, with nearLimit at 80%.

Billing is a ledger, not a gateway

Every customer is invoiced by hand today. models/invoice.model.js records what was asked and what was received; a payment gateway would later write to the same rows rather than becoming a second source of truth.

  • Invoice status: draft, issued, paid, void, uncollectible. Numbers look like INV-2026-0042, sequential within the year so gaps are visible. Amounts are integers in paise.
  • POST /api/platform/tenants/:id/invoices calls raiseInvoice: idempotent per period (a second call for the same periodStart returns the existing invoice), net 14 days, and returns nothing for trial or enterprise plans (they are not on the price list). Nothing schedules invoice creation; it is manual.
  • POST /api/platform/invoices/:invoiceId/pay records settlement and clears a past_due flag; .../void voids.
  • Separately from status (whether the product serves the workspace), tenant.billing.state (none, trialing, active, past_due, cancelled) records where it stands commercially.
  • The overdue sweep never suspends. The daily job overdue-invoice-sweep (07:30 UTC) only sets billing.state = 'past_due' on workspaces with an issued invoice past dueAt. Suspending an agency over a billing question is a decision for a person.
  • A workspace admin can see their plan but cannot change it: there is no self-serve upgrade because there is no payment gateway.

Per-workspace customisation

The pattern throughout is vocabulary in code, selection in config. Config chooses from fixed catalogues; it never carries free-form structure or code. Four axes, all under Settings for a workspace admin:

1. Branding tokens

tenant.branding holds product name, logo URLs, support contact and tokens (brand, brandContrast, accent, sidebar, sidebarText). The client writes these onto :root as CSS custom properties, which Tailwind utilities such as bg-workspace read, so a palette flows through every component without a rebuild. GET /api/tenant/config (public; toPublicConfig() never exposes limits, billing or internal notes) lets the sign-in screen draw itself before anyone is authenticated. The schema default brand token is #4f46e5, the stock indigo the design system otherwise bans, so it is what a workspace shows until it saves its own.

2. The screen catalogue

The sidebar is the intersection of three things: the catalogue (backend/tenancy/screenCatalogue.js: id, label, section, permission, flags), the frontend registry (frontend/src/app/screenRegistry.js: icon, route), the workspace's features map, and the user's permissions (hooks/useScreens.js). Current screen ids: dashboard analytics properties categories createListing import clients owners pipeline buyers tasks calendar transactions reports adminPanel settings.

  • Screen ids are a contract with stored tenant settings. Never rename one. Workspaces enable screens by id; renaming silently disables the screen everywhere. Change a label freely. To retire a screen, mark it deprecated and leave the id.
  • An id absent from features is on (a workspace must not lose a screen the day flags were introduced, and the stored map records only differences). core screens (dashboard, properties, adminPanel, settings) ignore the flag. adminOnly screens are for admins regardless of flags.
  • A workspace's own rename (tenant.settings.navLabels, e.g. calling Clients "Leads") beats a translation: useScreens.js compares label to defaultLabel. Endpoints: GET/PATCH /api/tenant/screens.

3. Category dynamic fields

A category's fields define how every listing in it is stored, so they are validated structure (reserved keys, duplicates and ReDoS-prone patterns are rejected by utils/categoryFields.js). Destructive changes answer 409 with a count (deleting a category in use, removing a field that holds values) and the UI offers ?force=true. Public category reads go through publicView(). Dynamic values are stored in attributes or in their native column; propertyTypeFields is retired.

4. The sales pipeline

backend/tenancy/stageCatalogue.js defines every stage the product understands: new_lead contacted qualified site_visit_scheduled negotiation booking_token documentation closed_won closed_lost, plus legacy initial_contact site_visit_done payment_pending that existing deals may still carry. A workspace chooses which stages, in which order, under which names (tenant.workflow.dealStages); closed_won and closed_lost are required, since a board with no end state keeps deals forever and makes every conversion figure wrong. Why not free-text stages? deals.stage is an enum on Client, and cross-workspace reporting needs a stage to mean one thing. Unlike screens, an unselected stage is off (a pipeline is an explicit, ordered list). Endpoints: GET/PATCH /api/tenant/pipeline.

Behaviour beyond settings is delivered by workspace rules, also chosen by name. Mail (tenant.mail), locale (currency, number locale, timezone, area unit, dial code, language), assignment mode (manual, round_robin, by_locality) and the onboarding checklist are the other tenant-level settings; see Workspace settings.

Anything outside the database needs its own tenant boundary

  • Response caches: use getTenantScopedCache(), never plain getCache(), for anything derived from one workspace's data. See Caches.
  • Sockets: emit to tenant:<id> or user:<id> rooms, and enter runWithTenant in handlers.
  • Jobs: a job body runs inside forEachTenant; a query with no context throws.
  • Webhooks, sequences, notifications are written and delivered per workspace.

CLI scripts must bootstrap tenancy

Never import a model directly in a script. A global plugin only applies to schemas compiled after it registers, and hoisted imports compile the model first, producing records with no tenantId that the application can never see. Use backend/scripts/_bootstrap.js:

const { models, inWorkspace, tenant, acrossWorkspaces, close } = await bootstrapScript();
await inWorkspace(async () => {
  await models.Listing.countDocuments();
});
await close();
  • It calls registerTenancy, then dynamically imports the models (Tenant User Role Category Listing Owner Client Task BuyerRequirement PropertyType), validates config, and connects.
  • It takes --workspace <slug>. With exactly one workspace it uses that one; with several and no flag it refuses to guess and lists the slugs; with none it tells you to run provisionTenant.js first.
  • Scripts that need other models import them after registerTenancy via dynamic await import(), as scripts/provisionTenant.js does.
  • Destructive scripts exist: npm run db:seed-fresh wipes and reseeds with no confirmation gate; npm run db:restore is destructive and requires --confirm plus typing the database name. The one-time migrations are db:migrate-tenancy (single to multi-tenant, supports --dry-run) and db:migrate-fields.
