Background jobs and automation

The lease-based scheduler and its jobs, lead scoring, follow-up sequences, outbound webhooks, workspace rules, imports, data rights and notification types.

The scheduler

backend/jobs/scheduler.js is deliberately dependency-free. Jobs here run every N minutes or once a day at a given hour, so a cron parser would buy expressiveness the app does not need and add a dependency to keep current. Before it existed there was no scheduler at all, which is why a set of schema fields never did anything: task.reminders[].sent, followUp.reminderSent, and tenant.trialEndsAt (only checked lazily, when somebody happened to make a request).

Two properties matter:

  • Single-firing across instances. The app ships under PM2 cluster mode and on hosts where more than one instance is normal. Each run takes a lease in Mongo (models/jobLock.model.js: name unique, lockedUntil, owner, lastRunAt, lastResult), so N instances still produce one run. It is a lease rather than a flag because a process can die mid-job: lockedUntil expires on its own, so a crash costs one cycle rather than wedging the job. JobLock is not tenant-scoped: the scheduler is infrastructure.
  • Non-overlapping. A run that is still going holds its lease, so a slow job is skipped rather than stacked on itself. The in-process tick also refuses to overlap itself.

How a job is claimed

setInterval every 60 s (unref'd)
→
tick(now): for each job, one atomic findOneAndUpdate
→
lease free AND due? owner = this instance
→
run handler, renewing lease
→
release: lastRunAt = now, lockedUntil = epoch
  • The decision is one atomic findOneAndUpdate with upsert. Read-then-write would let two instances both see a free lock and both take it. If two instances create the lock in the same instant, one gets a duplicate-key error (code 11000), which is treated as "lost the race", not as a failure.
  • Due means: for dailyAt: 'HH:MM' (always UTC), today's slot has passed and lastRunAt is before it; for everyMs, lastRunAt is at or before now - everyMs. Register with registerJob(name, { everyMs | dailyAt, leaseMs = 5 min }, handler). The name is the lock key, so never rename one casually. dailyAt wins if both are given.
  • Lease heartbeat. While a handler is running the lease is renewed every max(10 s, leaseMs / 3). A fixed lease is a bet on how long a job takes, and the bet is wrong the moment the work grows: reminder jobs send email, mail costs seconds per message, and when the lease expired mid-run another instance claimed it and the same reminders went out twice. The lease stays short, so a process that dies still frees the job within one interval.
  • A failing handler is logged, its lastResult is set to failed: <message>, and the lock is released; it does not crash the scheduler.

tick(now) takes the time as an argument. Never read the clock inside a job's cadence logic. The cadence decision and the stored lastRunAt must agree on what time it is. Reading the clock inside made a daily job stamp wall-clock time while tick reasoned about the time it was given, so the two disagreed and the job never became due again. This is also what lets tests/scheduler.test.js drive the scheduler with a fake time.

The registered jobs

All jobs are registered in one place, backend/jobs/index.js (registerAllJobs(), called once by startJobs() after the server is listening). Each job body runs inside forEachTenant() (tenancy/tenantContext.js), because a query with no tenant context throws by design: a sweep has to enter each workspace rather than querying across all of them. One workspace failing is recorded in the job's log line and does not stop the rest.

Reminders and webhooks are idempotent by construction: the reminder flag is set before the notification is sent ("if it fails we would rather drop one reminder than risk a loop that re-sends it every minute"), and webhook deliveries move to a terminal status.

JOBS_ENABLED

JOBS_ENABLED=false makes an instance serve traffic but take no leases (the scheduler is never started), useful when you want jobs confined to one host. Any other value, including unset, enables them. Because leases make firing single, you normally do not need this on a small cluster. On shutdown stopScheduler() clears the interval; note that a lease held by a run still in flight is not released by shutdown and simply expires.

Lead scoring and temperature

client.calculateScore() (models/client.model.js) is the only place the score is computed. It sums five factors and caps at 100 (the schema caps it too, so an over-100 total must not fail validation on a lead that is doing well):

FactorRule
engagement10 per communication in the last 30 days, max 30
budget20 if budget.max > 0
urgencypriority low 5, medium 10, high 20, urgent 30 (default 10)
fit5 per interested listing, max 20
recencydays since last touch (lastContactAt, else updatedAt, else createdAt): 7 days or fewer 20, 30 or fewer 12, 90 or fewer 5, otherwise 0

temperature follows the score (60 and up hot, 30 and up warm, else cold) unless someone set it by hand, which sets temperatureManual and pins it. Every recomputation honours the pin, including the nightly job. Sending temperature: "auto" on a client update clears the pin and lets the score decide again (the Temperature control shows an "Auto" link while a value is pinned).

It runs on lead creation, on a client update, on a deal stage change, when communications or follow-ups change (several crm.controller.js paths), in lead import, and nightly. The recency factor is why: the score decays, and nothing else would recompute it on a timer, so a lead that was busy last month would keep the score it earned while warm.

  • The nightly job (jobs/leadScoring.js) skips won and lost leads: their score is history, and rewriting it would quietly change what past reports say.
  • It writes only score, scoreFactors and temperature through updateOne, skipping validation and middleware so an unrelated, already-invalid field cannot make it fail.
  • It walks every open lead in keyset pages of 1000 by _id (batchSize), so a workspace with more open leads than one page is fully rescored. Its write uses timestamps: false: recency falls back to updatedAt when there is no lastContactAt, so bumping it would make every lead look freshly touched.

Follow-up sequences

A sequence (models/sequence.model.js) is an ordered list of steps, each with an action (email, task or reminder), a delayDays from the previous step (0 to 365; from enrollment for the first), a subject and a body (up to 5000 characters) that support the same {{name}} merge fields as email templates, resolved against the lead (recipientName, firstName, lastName, phone, email). Delays rather than absolute dates mean a sequence can be enrolled at any time. Admins create, edit and delete sequences; admins and employees enroll a lead with POST /api/sequences/:id/enroll (re-enrolling restarts it). Enrollment statuses: active, completed, stopped.

jobs/sequences.js fires due steps per workspace. The rules it exists to guarantee:

  • A step fires exactly once. The enrollment advances (currentStep, nextStepAt, a history entry) in the same pass, so a retry or a second instance cannot send the same email twice.
  • It never chases a closed lead. Continuing to chase someone who already bought or said no is the worst thing an automation like this can do. stopSequencesForClient() is called synchronously from updateDealStage when a deal becomes closed_won or closed_lost, so the gap between "marked won" and "sent another chase email" does not exist. As a backstop, every due enrollment is re-checked when the job reaches it and stopped if the lead is won, lost or deleted (stoppedReason such as "lead marked won" or "lead removed"), if the sequence was deleted, or if the sequence is paused (isActive = false). Deleting a lead (singly or in bulk), and bulk-moving leads to won or lost, call it too; the job's own check is only the backstop.
  • A failing step does not wedge the enrollment. It advances anyway with failed: <message> recorded in the history, so one bad address cannot freeze an enrollment.
  • An unsubscribed address gets no email. The workspace suppression list (EmailSuppression) is checked at send time, every time. Every sequence email ends with who is writing and a working unsubscribe link, and carries List-Unsubscribe and List-Unsubscribe-Post: List-Unsubscribe=One-Click headers (RFC 2369 and RFC 8058, required by Gmail and Yahoo from bulk senders). Task and reminder steps still fire since they go to the agent, not the lead.

Step outcomes recorded in history include email sent, skipped: no email address, skipped: unsubscribed, email failed: <reason>, task created and reminder sent. The unsubscribe endpoints (GET/POST /api/unsubscribe/:token) are public, rate limited, and answer before tenant resolution because the signed token names the workspace and lead.

Outbound webhooks

A workspace admin subscribes endpoints (/api/webhooks, reference) so the CRM can feed Zapier, Make, n8n or the agency's own scripts. The design separates two halves so a slow or dead customer endpoint can never slow down, or fail, the user's action:

request (e.g. create lead)             scheduler, every 60 s
  emitEvent(event, payload)     -->      deliverDueWebhooks()
  inserts WebhookDelivery rows           POST each due row, sign it,
  (never throws, never waits             record the result, retry or give up
   on the network)
  • emitEvent finds this workspace's active webhooks subscribed to the event (or to *) and inserts one WebhookDelivery per hook. It never throws.
  • The queue lives in Mongo, not in memory, because the process that raised the event may not be the one that delivers it and a restart must not lose deliveries. It doubles as the delivery log; rows expire after 30 days (TTL index).

Events (WEBHOOK_EVENTS)

A closed catalogue in models/webhook.model.js: a subscription is stored config, so an event name is a contract, and renaming one silently breaks customers' automations. A subscription may use *, which is stored as-is (not expanded) so new event types reach existing subscribers.

Every event in the catalogue has a call site: deal.created (adding a deal), listing.updated, task.created, task.completed (status becomes done), buyer.created and share.viewed (a recipient opens a share link; fire and forget, carrying the share id, label and counts but never the token or the recipient's contact details). The payload is { event, sentAt, data } where data is the small object each call site passes (for example { id, name, phone, source } for a lead).

Delivery and signing

Each attempt is a POST with a 10 s timeout, redirect: 'error' (a redirect to somewhere else is not a delivery), and these headers:

HeaderValue
Content-Typeapplication/json
User-AgentRealVista-Webhooks/1
X-Webhook-EventThe event name
X-Webhook-DeliveryThe delivery id
X-Webhook-TimestampUnix seconds
X-Webhook-Signaturesha256= + hex HMAC-SHA256 of <timestamp>.<raw body> using the endpoint secret

The timestamp is inside the signed string, so a captured delivery cannot be replayed later against a receiver that checks it. This is the same scheme Stripe and GitHub use. The secret (whsec_ followed by 48 hex characters) is stored in the clear by design: the receiver needs the same value, so an admin has to be able to read it back. It is a signing key, not a credential to anything of ours. POST /api/webhooks/:id/rotate-secret replaces it.

// Receiver (Node): verify before trusting the body
const signed = `${req.headers['x-webhook-timestamp']}.${rawBody}`;
const expected = 'sha256=' + crypto.createHmac('sha256', secret).update(signed).digest('hex');
const ok = crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(req.headers['x-webhook-signature']));

Retries, failure and disabling

  • 5 attempts maximum. After a failed attempt the next is scheduled after 10 s, 1 min, 5 min, then 30 min; after the fifth failure the delivery is failed.
  • Delivery statuses: pending, delivered (any 2xx), failed, abandoned (the endpoint was deleted or switched off after the row was queued).
  • The endpoint tracks failureCount, reset on any success. At 10 consecutive failures it sets isActive = false with disabledReason, so a dead endpoint stops consuming retries.
  • The response body is truncated to 2000 characters in the log, so a receiver returning megabytes cannot fill the collection.
  • validateWebhookUrl guards against server-side request forgery: http or https only; literal private and loopback ranges, link-local (including cloud metadata at 169.254.x), .local, .internal and .localhost are refused; in production the URL must be https. It is a guard rather than a guarantee, since a public hostname that resolves to a private address is not caught (which is also why redirects are refused at fetch time).
  • Admin endpoints: GET/POST /api/webhooks, PATCH/DELETE /api/webhooks/:id, POST /:id/rotate-secret, POST /:id/test, GET /:id/deliveries.

Workspace rules and plugins

tenant.workflow.rules lets a workspace select named implementations registered in code (plugins/builtin.js) for fixed extension points. Config never carries code, so an admin editing settings cannot execute anything the deployment did not ship. This is the "vocabulary in code, selection in config" rule. (Earlier, the field existed in the schema with five hook names and nothing ever read it: a workspace could configure a rule and get neither behaviour nor a warning.)

Each rule entry is { hook, implementation, config, enabled, order }. Rules for a hook run in order. A rule receives the operation's context and may return a partial patch that is merged into it, so a listing.beforeSave rule can normalise a field without knowing about the others. GET /api/rules (admin) returns the hooks, the available implementations and the workspace's configured rules; rules are saved through PATCH /api/tenant/config (workflow.rules) from WorkspaceRulesPanel.jsx.

Veto versus error: two different things

A rule can call veto('message') (throws RuleVetoError, status 400). runHook treats the two outcomes differently, and they must stay distinct:

  • A veto propagates. It is the rule working: the whole point of "ask for a reason before marking a deal lost" is that it reaches the user as a validation error (HTTP 400) they can act on.
  • Any other thrown error is logged and the rule is skipped. That means somebody's automation is misconfigured, which must not stop them saving a property.
  • An unregistered implementation name in stored config is logged as a warning and skipped. Names are not validated when the config is saved.

Catching both in one handler once made every veto rule silently do nothing. registerRule throws on an unknown hook, a missing run, or a duplicate name. A rule's name is a contract with stored config: never rename one. To add a rule: write it in plugins/builtin.js with registerRule(name, { hook, describe, run }); if it needs options, the panel in the frontend needs a matching editor.

Imports

There are two importers: listings (/api/listing/import/suggest-mapping|preview|commit, wizard at /admin/import) and leads (/api/lead-import/suggest-mapping|preview|commit, wizard at /admin/import-leads). Both follow the same shape: suggest a column mapping, preview, then commit. Both validate every row first and then write in batches with per-row results.

  • Leads: up to 5000 rows per request (MAX_ROWS), written in insertMany batches of 500 with ordered: false, so one bad row costs that row and not the rest of the file. It used to save one row at a time and the first row the database refused threw out of the loop: rows before it were written, rows after it were not, and the response did not say which.
  • Listings: at most 500 rows per request (IMPORT_CHUNK_LIMIT; the client chunks) and 20000 per import job (IMPORT_TOTAL_LIMIT). duplicateMode is skip, update or create; updates never reassign userRef, the original creator.
  • Row errors are returned in rowErrors, capped at 200 entries (MAX_ROW_ERRORS); the counts stay exact and rowErrorsTruncated says the list was cut. A 5000-row file of the wrong export should not produce a 5000-entry response. The summary mirrors the ingest pipeline shape (inputCount, inserted, updated, failed) on top of the older created and skipped fields the UI reads.
  • Duplicates and errors are skipped, not merged (lead import): deciding two records are the same person is a judgement an importer should not make silently on 400 rows. Duplicate detection uses indexed lookups only (phoneKey, email), one query per key kind, not one regex per row.
  • The monthly meter: maxImportRowsPerMonth is enforced by reserveImportRows(n) in tenancy/limits.js, which atomically reserves rows in models/importUsage.model.js before any row is written (refusing halfway through a file would leave the agency guessing which half they have) and returns release(unused) to hand back what did not land, so duplicates and refused rows do not cost allowance. A refusal is 402 PLAN_LIMIT with details: { limit, used, requested, remaining }. Both importers charge the same meter.
  • insertMany skips pre('save'), so the lead importer sets derived fields (phone key, score via calculateScore(), assignment per the workspace's rule) itself. tests/leadImportCommit.test.js compares an imported lead with a saved one so the two cannot drift. Each created lead also emits lead.created.
  • If a column header or field aliases a native listing column, update NATIVE_FIELD_ALIASES in both frontend/src/utils/nativeFieldAliases.js and backend/utils/importMapping.js.

The enforced import meter is the ImportUsage collection keyed by {tenantId, month}, where the month in the workspace's own timezone is part of the key, so it resets by changing key rather than by a job. The old import-usage-reset job, which only rolled the legacy tenant.importUsage field, has been removed; that field is deprecated and no longer read or written.

Data rights

controllers/dataRights.controller.js and routes/dataRights.route.js (/api/data-rights) implement access and erasure. Before this there was no export, no erasure, and a "Delete Account" button that only deactivated while telling the user it removed everything.

EndpointWhoEffect
GET /export/meAny signed-in userEverything the workspace holds about the caller, as JSON (tenantId and __v stripped).
GET /export/user/:idexportData permissionExport a team member.
GET /export/:kind/:idexportData permissionExport a contact.
DELETE /erase/user/:idWorkspace adminErases a team member's personal details.
DELETE /erase/:kind/:idWorkspace adminErases a contact (client, owner or buyer).
  • Erasing a team member closes the account (inactive, soft-deleted, refreshTokens emptied) and replaces personal fields (username, email, phone and the address fields). Records they created stay, attributed to "Former team member <id>": a workspace's audit trail and property book belong to the agency, and a trail with a dangling author is worse than one naming a former member. The shared erasedUserFields(id) is used by admin erasure and self-service account deletion so they cannot drift. Username and email carry the full id because both are unique per workspace; a constant made every erasure after the first fail with a duplicate-key error and left the data in place. phone becomes null, not an empty string, because the phone index is partial on strings. Their notifications are deleted and security logs keyed on their email are re-keyed. An admin cannot erase themselves, and a platform operator cannot be erased from here.
  • Erasing a contact removes the personal details outright and keeps an anonymous shell ("Erased contact") so counts and pipeline history stay correct, and soft-deletes their documents and makes them non-public.
  • Each key in ERASABLE_CONTACTS must be a real path on its model: an unknown $set key is dropped silently under Mongoose strict mode, so a wrong field name does not fail, it leaves the data in place. tests/erasureFields.test.js checks this.
  • Erasure is deliberately irreversible and admin-only. The policy text on /privacy makes claims about these buttons, so a change here changes pages/Legal.jsx in the same commit (see Security and data protection).

Notification types

utils/notificationTypes.js is the one catalogue. It feeds the Notification model's enum, the per-user preference toggles and the Settings screen, so the three cannot disagree. In-app delivery always happens unless the user turned it off ("the bell is the record of what occurred"); defaultEmail decides whether mail is also sent when the user has expressed no preference. An email preference is honoured only when stored as exactly true.

Adding to this machinery

  • A new scheduled job: write an async function that does one workspace's worth of work and returns a count; register it in jobs/index.js with a stable name and cadence, wrapped in forEachTenant (use serviceableOnly: false only when a suspended workspace genuinely needs the work). Make the work idempotent (mark done before, or in the same step as, the side effect). Do not read the clock inside cadence logic.
  • A new webhook event: add it to WEBHOOK_EVENTS, then call emitEvent(name, smallPayload) at the write site. Do not await a network call in the request.
  • A new notification type: add it to NOTIFICATION_TYPES and call notify().
  • A new rule or hook: add the hook to HOOKS and the enum in tenant.model.js, and call runHook at the write site; add the rule in plugins/builtin.js.
