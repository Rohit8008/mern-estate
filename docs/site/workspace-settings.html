Workspace settings

What each Settings tab changes, who can see it, and the limits and gotchas behind branding, screens, locale, pipeline, rules, email, webhooks and system tools.

How Settings is organised

Settings (/settings) is a tabbed page. The URL is the state: ?tab=<group>&section=<id>, so a tab is linkable (the onboarding checklist links to /settings?section=branding). A group with nothing visible to you is not shown at all, and a person with only one group sees no tab strip.

Tab (group)SectionsWho sees it
AccountNotifications, Privacy, Security, Appearance, Language & regionEvery signed-in user. These affect only your own account.
WorkspaceWorkspace (branding, units, plan usage), Menu & screens, RulesWorkspace admin only
SalesSales pipeline, Lead sources, Tags, Follow-up sequences, Email templatesWorkspace admin only
IntegrationsEmail, WebhooksWorkspace admin only
SystemSystem, Search insights, Data requestsWorkspace admin only

"Admin" here means role: 'admin' of this workspace. Each write endpoint behind these panels checks the admin role itself ("Only a workspace admin can …"), so hiding a tab is a convenience, not the protection. Anything that belongs to the vendor (plan, feature switches on the plan, limits, slug, status, custom domain) is platform-only and is rejected with a clear message if sent to PATCH /api/tenant/config. See Multi-tenancy and platform admin.

Account tab (everyone)

  • Notifications. Per event type, choose "In app" and "Email". Defaults come from utils/notificationTypes.js. Email is on by default for: lead assigned, deal stage changed, task assigned, task due, follow-up due, system alerts. Off by default: new buyer match, new message, import finished, shared property viewed, listing updates. Notifications go through one entry point (utils/notify.js): it honours these preferences, stores a notification, pushes it over the socket and mails through the workspace's template if one exists.
  • Privacy. Profile visibility (show email, phone, online status, allow direct messages) and "Account closure and data requests" including Close Account.
  • Security. Change password, active sessions (this device) and Sign out all devices, which revokes every refresh token.
  • Appearance. Theme (light, dark or system) and compact mode.
  • Language & region. Your own language, overriding the workspace default, which an admin sets in the same panel. Shipped languages are the files in frontend/src/i18n/locales/ (currently English and Hindi); a new language is one dropped-in JSON file. Clearing your override falls back to the workspace default.

Workspace section: branding, units and plan

Settings, Workspace, "Workspace" section (id branding). Saved with PATCH /api/tenant/config; the fields in the body are merged into the stored document, so sending only one colour does not wipe the logo. An unsaved-changes bar appears at the bottom with Discard and Save changes.

Colours are six-digit hex values (the field turns red otherwise). The panel has a live preview and a contrast check, and Reset to default. The tokens are written onto :root as CSS variables, so Tailwind classes such as bg-workspace follow the agency's colour with one build serving every workspace. Other fields: agency name (up to 120), product name (shown instead of "Real Vista", up to 60), logo URL, square mark URL (collapsed menu and favicon), support email. Support phone and a login background URL exist in the schema but this panel has no field for them. The product name, logo and support contacts also dress share links and the invite page.

The backend branding schema now defaults tokens.brand to #2b6faa, matching the frontend fallback used before config loads. Workspaces created before that change may still store the old default (#4f46e5, stock indigo) until an admin saves branding.

Menu and screens

Settings, Workspace, "Menu & screens". The sidebar is built from backend/tenancy/screenCatalogue.js (id, label, section, permission) and frontend/src/app/screenRegistry.js (icon, route), intersected with the workspace's switches and the user's permissions. Two things you can do per screen:

  1. Switch it off or on. A screen not mentioned is on (a stored override exists only when it differs from the default). Turning one off hides it and makes its URL unreachable for the workspace.
  2. Rename it (up to 40 characters), for example "Clients" to "Leads". A workspace's own rename beats a translation. A rename equal to the default label is not stored.

Rules

Settings, Workspace, Rules (admin only; GET /api/rules lists what exists, enabling writes workflow.rules through PATCH /api/tenant/config). A rule is a named implementation shipped with the deployment (backend/plugins/builtin.js); the workspace config only selects which are on and their options and never carries code, so an admin cannot introduce behaviour the deployment did not ship.

RuleRunsWhat it doesOptions
normaliseLocalitywhen a property is savedTrims and title-cases the locality so "whitefield " and "Whitefield" group togethernone
requirePriceOnPublishwhen a property is savedRefuses (veto) an available property whose price is not above 1: "This property needs a price before it can be published"none
defaultCityFromWorkspacewhen a property is savedFills an empty city with a defaultDefault city (up to 80 characters)
requireNoteOnLosswhen a deal changes stageRefuses moving to Lost without a note: "Add a note explaining why this deal was lost"none
blockSkippingToWonwhen a deal changes stageRefuses moving straight to Won from New Lead or Contacted: "Move the deal through negotiation before closing it as won"none
tagLeadBySourcewhen a lead is createdSets the lead's priority from its sourceSource name to priority (low, medium, high, urgent) pairs; source names are lowercased
skipRowsWithoutPricebefore a property importWould skip imported rows with no pricenone
  • A rule that calls veto('…') refuses the operation and the user sees its message as a 400. Any other error inside a rule is logged and the rule is skipped. The two are deliberately distinct; catching both once made every veto rule silently do nothing.
  • Toggling a rule keeps its saved options. Option drafts are sent only when you press that rule's Save.
  • Hooks defined: listing.beforeSave, listing.afterSave, listing.beforeImport, deal.beforeStageChange, lead.onCreate.

Where hooks actually fire today: listing.beforeSave and listing.afterSave run when a property is created and when it is edited (on an edit a rule sees the stored record with the changes applied, and a veto answers 400). listing.beforeImport runs for each import row, so skipRowsWithoutPrice skips priceless rows. deal.beforeStageChange and lead.onCreate do run where described.

Sales pipeline

Settings, Sales, "Sales pipeline" (GET / PATCH /api/tenant/pipeline, admin only). The stage vocabulary is fixed in backend/tenancy/stageCatalogue.js; the workspace chooses which stages to use, their order, their label (up to 60 characters) and their colour. Nine stages are on by default; three legacy stages are offered as "Older stage".

KeyDefault label
new_leadNew Lead
contactedContacted
qualifiedQualified
site_visit_scheduledSite Visit
negotiationNegotiation
booking_tokenBooking / Token
documentationDocumentation
closed_wonWon (required)
closed_lostLost (required)
initial_contact, site_visit_done, payment_pendingInitial Contact, Site Visit Done, Payment Pending (legacy)
  • A pipeline needs at least one stage and must include both Won and Lost; otherwise 400 ("without an end state, deals never leave the board and every conversion figure is wrong"). A stage can appear only once, and unknown keys are rejected.
  • Unlike screens, an unselected stage is off: a pipeline is an explicit ordered list. Until you save one, the workspace uses the default nine.
  • Order is the order you arrange them in; the server stores it as 10, 20, 30, and so on.
  • Deals sitting in a stage you remove stay where they are (the panel warns about this). The board only draws the enabled columns.
  • Won and Lost carry meaning in code (auto-created transaction, listing status, sequences stopped). See Deals, stages and commission.

Lead sources, tags, sequences

These three sections are admin-only in Settings; their mechanics are in Leads and pipeline.

  • Lead sources: name, monthly cost, description, active. Seeded with 11 defaults on first read. Deleting a source in use answers 409 with a count, and the panel offers ?force=true. Editing the cost changes the ROI report immediately.
  • Tags: name (40 characters), one of nine colours, description. Rename and recolour apply everywhere because records reference the tag by id.
  • Follow-up sequences: ordered steps (task, email, reminder) with a delay in days. Deleting one with leads part-way through answers 409 with the count; forcing stops those enrollments.

Email templates

Settings, Sales, Email templates (/api/email-templates, admin only). Each notification type, plus user.invited, user.welcome and report.shared, can have a workspace override of the subject and HTML body. Types: lead assigned, deal stage changed, task assigned, task due, follow-up due, new buyer match, new message, import finished, shared property viewed, listing updates, system alerts.

  • Variables are written {{name}} and resolved from a closed list: recipientName, workspaceName, title, body, link, actorName, date. There is no expression syntax, so a template cannot reach into a document or call anything. Substituted values are HTML-escaped. An unknown name is left as written so a typo is visible.
  • The HTML is sanitised when saved against an allowlist (links, paragraphs, headings, tables, images, basic formatting and inline style). Scripts and event handlers are stripped.
  • Buttons: Preview, Send test (to yourself), Save and Revert (deletes the override and returns to the built-in wording).
  • If a template is saved but the user's own notification preference has email off, no mail is sent. Templates change wording, not recipients.

Email (SMTP)

Settings, Integrations, Email (GET / PATCH /api/tenant/mail, POST /api/tenant/mail/verify, admin only). By default every workspace's mail uses the deployment's SMTP credentials (SMTP_* in .env), so it arrives from the vendor's address. A workspace that fills this in sends as itself.

FieldNotes

Verify opens the connection and authenticates without sending anything, which tells a wrong password apart from "sent, check spam". Saving drops the cached transport for the workspace, and the change is written to the activity log. The System tab shows which source mail is currently using.

Webhooks

Settings, Integrations, Webhooks (/api/webhooks, admin only) forward events to Zapier, Make, n8n or your own service.

Setting one up

  • Add an endpoint: name, URL and events (choose individual events or "All events", stored as *, which keeps receiving event types added later).
  • The URL must be http or https, must not be a private or internal address, and in production must be https. This blocks literal private ranges; it cannot stop a public hostname that resolves to a private address, so it is a guard, not a guarantee.
  • Each endpoint has a signing secret shown on screen. Rotate secret issues a new one and the old one stops verifying immediately, so update the receiver first or accept a gap. Send test queues a test event. Deleting an endpoint discards queued deliveries.

Delivery, signing and the deliveries log

  • The body is JSON: { "event", "sentAt", "data" }. Headers: X-Webhook-Event, X-Webhook-Delivery (the delivery id), X-Webhook-Timestamp and X-Webhook-Signature: sha256=<hex>.
  • The signature is HMAC-SHA256, keyed with the endpoint secret, over the string <timestamp>.<raw body>. The timestamp is inside the signed string, so a captured delivery cannot be replayed against a receiver that checks it. This is the same scheme Stripe and GitHub use.
  • Deliveries are queued when the event happens and sent by the webhook-delivery job, which runs every minute. Each attempt times out after 10 seconds.
  • Retries: up to 5 attempts in all, with waits of 10 seconds, 1 minute, 5 minutes and 30 minutes between them. After that the delivery is marked failed.
  • Auto-disable: after 10 consecutive failed attempts the endpoint is switched off ("Disabled automatically after repeated failures") and its queued deliveries become abandoned. A success resets the counter. Re-enable it with the toggle once the receiver is fixed.
  • Deliveries log: expand an endpoint to see its latest deliveries (15 shown in the panel; the API allows up to 100) with status pending (waiting for its next attempt), delivered, failed or abandoned, plus last status code and error. Use it before assuming the receiver is broken.
  • Receivers should be idempotent: the same delivery can arrive more than once if your server timed out after processing.

System tab

System

GET /api/metrics/system (admin only) renders as: version, environment, uptime, database state and latency, mail source, Node runtime (version, platform, memory), the scheduler and integrations. The scheduler lists every registered job with its cadence (for example "daily at 03:00 UTC" or "every 15 min"), when it last ran and whether its last result starts with failed: (shown as Failing). Integrations are booleans only (SMTP, SMS, observability, Cloudinary, response encryption), never the values. The panel links to the machine-readable API reference (/api/docs/openapi.json, admin only). It is generated from the router and its validation schemas and is also written by npm run docs:openapi; do not edit it by hand.

A job that reports healthy but has never run on this host usually means scheduling is switched off (JOBS_ENABLED=false) or another instance holds the lease. See Background jobs.

Search insights

GET /api/search/analytics (admin only): the most frequent queries, how results split across record types, the average response time, and queries that returned nothing, which is the most useful list: it shows what your team looked for and could not find (a missing category, a locality spelled differently).

Data requests

Search for a team member, client, owner or buyer, then export everything held about them as JSON or erase their personal details (irreversible; admin only). The rules, what is retained and who may export are in Data export and erasure.

Config that exists but nothing reads

The workspace workflow schema also holds listingStatuses, requireApprovalToPublish and requireApprovalOverPrice. They are accepted in PATCH /api/tenant/config and returned in the public config, but no screen edits them and no code outside the model reads them, so setting them has no effect today. Listing statuses are the fixed four (available, sold, rented, under_negotiation).
