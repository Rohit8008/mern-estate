Security and data protection

The controls the code actually enforces (tenant isolation, route guards, validation, rate limits, uploads, sharing, data rights), why each exists, and the limits that are not covered.

How to read this page

Everything here was checked against the code. Where a rule exists because of a bug that already happened, the bug is named, since the rule is easier to keep when the reason is known. The final section, What is not protected, is as important as the rest. Sign-in, cookies and CSRF are on their own page: Authentication and sessions.

Tenant isolation

All agencies share one database; every document carries a tenantId. Isolation is enforced by code, not by the database, in a global Mongoose plugin (backend/tenancy/tenantPlugin.js, registered in index.js before any model is imported):

  • A query with no tenant context throws. It does not silently run unscoped.
  • A query that names a different tenant than the context throws. An operation the plugin cannot scope (estimatedDocumentCount) throws.
  • Only the Tenant model is global. Everything else is scoped by existing, not by remembering to opt in.
  • Deliberate cross-tenant work is spelled runWithoutTenantScope('why') and is greppable. Examples: opening a share link, accepting an invite, resolving which tenant a request belongs to.
  • Uniqueness is { tenantId, field }; a bare unique: true would let one agency's email block another's.

Other places the boundary has to hold, all in code:

  • Response caches. A cache sits in front of the database, so query scoping cannot protect it. getTenantScopedCache() (utils/cache.js) suffixes every key with the current tenant id (or none / unscoped); plain getCache() is only for genuinely global data such as geocoding. The tenant record itself is cached in process for 60 seconds, so suspending a workspace takes effect within a minute.
  • Sockets. Rooms are tenant:<id> and user:<id>. A bare io.emit() reaches every agency, so controllers use emitToTenant() / emitToUser() only. A message:send to a user id from another workspace is refused ("That person is not in this workspace.") because the recipient lookup runs in the sender's tenant. Presence lists and typing pings are scoped the same way.
  • Scripts, jobs and socket handlers must enter a tenant explicitly (runWithTenant, withTenantBySlug, forEachTenant). CLI scripts load models through scripts/_bootstrap.js; a hoisted import of a model compiles its schema before the plugin and writes records with no tenantId that the app can never see.
  • Platform vs workspace admin. role: 'admin' administers one agency. isPlatformAdmin is a separate, select: false flag that guards /api/platform/* and the log-query endpoints. requirePlatformAdmin re-reads it from the database on each call and never trusts the token. See Multi-tenancy.

Who can reach what

  • Every mounted route is guarded or declared public. backend/security/publicRoutes.js lists the endpoints that are public on purpose, each with a reason. tests/routeAccess.test.js walks the live Express router and fails the build for any route that is neither guarded (verifyToken, tryVerifyToken, requireAdmin, requirePermission, requirePlatformAdmin, canCreateListing) nor listed. If it fails, add the missing guard; do not add the route to the allowlist. The CSRF exemptions are derived from the same list.
  • Permissions come from one catalogue. utils/permissionCatalogue.js (35 permissions) generates the role schema, and requirePermission() throws at module load on an unknown key. tests/permissionCatalogue.test.js walks the route files. This exists because one route asked for manage_settings, which was never a permission, so every non-admin was denied forever. See Team, roles and permissions.
  • The property book is not public. Nothing about a listing, category or property type is reachable without a session. Sharing outside the agency goes through share links (below).
  • Object-level checks. Single-item handlers check ownership or staff status. A 2026-08 review found one missing check (GET /api/buyer-requirements/:id, an IDOR); buyerRequirement.controller.js now applies one isStaff(user) helper (admin and employee are org-wide) consistently across its single-item handlers.
  • Documents are not public. Files under /uploads/docs/ redirect (307) to /api/documents/file/:filename, which goes through verifyToken and the ownership check, and responds with X-Content-Type-Options: nosniff and Content-Disposition: attachment so a document never renders inside the app's origin.

Validation and injection

  • Every POST/PUT/PATCH needs validateBody(schema). It runs Joi with abortEarly and stripUnknown: true and replaces req.body with the cleaned value. tests/validationCoverage.test.js fails a new write route that has none unless it is allowlisted with a reason. Because unknown fields are dropped, a field the controller reads but the schema omits is silently lost, which is also what blocks mass assignment (for example, nobody can send isPlatformAdmin or tenantId).
  • Operator injection. The body is parsed before express-mongo-sanitize runs ($ne, $where and similar keys are replaced with _, logged as an injection attempt). Earlier, sanitizing ran while req.body was still undefined, so {"email":{"$ne":null}} reached controllers. Dotted keys are allowed (allowDots) because an import's column mapping is keyed by header text like "Phone no.". hpp collapses duplicate query parameters (?role=user&role=admin). tests/requestPipeline.test.js pins this order.
  • XSS on input. The xss rewrite is applied to query and params only. Bodies legitimately carry markup (email templates up to 100 KB, notes such as "<3 BHK") and escaping on the way in would corrupt what the user saved. Escaping is done on output: React escapes what it renders, mail templates render through utils/emailTemplates.js, and the API's 404 page escapes the URL it echoes.
  • Regexes. User text never goes into a regex raw: use utils/escapeRegex.js (containsInsensitive, equalsInsensitive), which also coerces query objects to strings. Category field patterns are screened for ReDoS-prone shapes (utils/categoryFields.js).
  • Paging and sorting are clamped (limit max 500) and sort keys are an allowlist (utils/listQuery.js), so a caller cannot force a scan of an unindexed field or learn the order of a field they cannot read.
  • CSV exports defuse spreadsheet formula injection: a cell starting with =, +, -, @ or a control character is neutralised (utils/csvExport.js).
  • Body size limit is 10 MB for JSON and urlencoded; larger gets 413.

The CSP is what the Express process sends. If nginx serves the built frontend directly, the static pages do not carry it unless the proxy adds it.

CORS (config/environment.js)

  • Production allows only FRONTEND_URL and ADMIN_URL. Development allows http://localhost:5173, http://localhost:3000 and anything in EXTRA_CORS_ORIGINS (comma-separated).
  • credentials: true; methods GET, POST, PUT, DELETE, PATCH, OPTIONS; allowed headers include X-CSRF-Token and X-Request-Id. The same origin list guards Socket.IO.
  • CORS is a browser control. A native app or curl sends no Origin and is not stopped by it; that is why state-changing safety rests on the session cookie plus the CSRF token, not on CORS.

A 429 returns code: "RATE_LIMITED" and the request id, plus the standard RateLimit-* and Retry-After headers from express-rate-limit (standardHeaders: true). In development the ceilings are raised (1000 / 5000). ENABLE_RATE_LIMITING=false switches off only the app-level /api and /api/upload limiters; the per-route auth, refresh and share limiters stay on. With REDIS_URL set the counters live in Redis (prefix rl:); without it they are per process, so on N instances every limit is N times looser. Behind a proxy, production sets trust proxy to 1, which is correct for one hop (nginx) and wrong for two (CDN plus nginx): the limiter would then see the proxy's address.

Uploads

The stored-XSS fix (found in a 2026-08 review) is the model for every upload path:

  • Uploads are buffered in memory (multer memoryStorage) and inspected by magic bytes (file-type, utils/fileValidation.js) before anything touches disk. The client's declared Content-Type and filename are untrusted.
  • The stored extension comes only from the detected type. Previously a spoofed multipart type of image/png on a .html file got saved with its real extension and served by express.static as executable HTML or JS, which satisfied script-src 'self' without any CSP bypass.
  • Stored name: <timestamp>_<4 random bytes hex>_<sanitised base name><ext>.
EndpointFieldLimitAllowed (detected) types

POST /api/upload/multipleimages (max 6)10 MB eachJPEG, PNG, GIF, WebP

Every upload is weighed against the plan's storage cap first and answers 402 when exceeded (assertStorageAvailable). Images and voice notes saved here leave no size record, so they are checked per upload but not counted in "used" storage. In the web app, listing photos and voice notes are uploaded straight from the browser to Cloudinary with an unsigned preset (frontend/src/utils/cloudinary.js) and never pass through these checks.

Share links

Share links replaced anonymous browsing (/api/share, opened at /s/:token). The token is the credential, and everything is built around that:

  • 32 random bytes, URL-safe, unique-indexed. Stored in the clear (it must be resolvable from the URL alone); protection is entropy plus expiry.
  • Expires by default 30 days after creation (explicit null means never). Revoked links stay in the database with revokedAt/revokedBy, so "who did we send this to and when did we stop it" stays answerable. Expired or revoked links answer 410.
  • Optional passcode (min 4 characters), stored as a bcrypt hash and sent as x-share-passcode (or ?passcode=). Missing returns 401 with passcodeRequired: true; wrong ones are logged (share_passcode_failed, token truncated to 8 characters).
  • Unknown tokens answer 404 "This link is not valid." so the endpoint cannot enumerate tokens. Every open increments viewCount and lastViewedAt.
  • forRecipient() is an allowlist of fields: owner contacts, internal notes, assignment and commission are never included, and a new Listing column does not become public by being added.
  • createShare re-reads listings through listingScope, so you cannot share what you cannot see. At most 50 listings per share.

Outbound webhooks

Admin-only (/api/webhooks). A URL the server fetches is an SSRF vector, so validateWebhookUrl rejects non-http(s), localhost, .local/.internal hosts and the literal private, loopback and link-local ranges (10/8, 127/8, 169.254/16 which covers cloud metadata, 172.16/12, 192.168/16, fc00::/fd, fe80::); in production it requires https. Redirects are refused at delivery (redirect: 'error'), and each delivery has a 10-second timeout. Payloads are HMAC-signed with a per-webhook secret; a verification example is on API conventions.

Secrets and configuration

  • The process exits at boot if JWT_SECRET, REFRESH_SECRET, MONGO_URI, NODE_ENV or MESSAGE_ENCRYPTION_KEY is missing. validateConfig() additionally requires both JWT secrets to be at least 32 characters, rejects the placeholder defaults in production, and requires APP_DOMAIN or DEFAULT_TENANT_SLUG in production (without one, every query throws and the API is down rather than degraded).
  • Keep the two JWT secrets different. A review found them identical; fixing it invalidated all refresh tokens once. The same applies to any rotation: users sign in again.
  • Chat messages are encrypted at rest with AES-256-GCM (key derived once with scrypt from MESSAGE_ENCRYPTION_KEY; stored as v2: + hex; legacy format still decryptable).
  • Optional API response encryption (ENCRYPT_API_RESPONSES) is described under API conventions. It is obfuscation of a body that already travels over TLS, and its key is baked into the public JS bundle; do not count it as a confidentiality control.
  • Unsubscribe links are signed with UNSUBSCRIBE_SECRET (falls back to a key derived from JWT_SECRET). Set it once and never rotate: rotating breaks every link already sent.
  • Production Docker image runs as the non-root node user, so a path traversal or RCE does not write as root.
  • Errors: in production an unexpected 500 never shows its message; the client gets a generic sentence and the request id (globalErrorHandler). Stack traces appear only when NODE_ENV=development.

Logs and audit trail

  • SecurityLog collection: sign-in outcomes, refresh, logout. 180-day TTL (SECURITY_LOG_RETENTION_SECONDS), chosen as the floor CERT-In's April 2022 directions set for ICT logs. Changing it is a compliance decision.
  • Structured logger (utils/logger.js) ships to OpenObserve streams backend_logs, security_logs, audit_logs, access_logs, frontend_logs when OPENOBSERVE_USERNAME/PASSWORD are set; otherwise it writes to stdout and drops the rest. Every line is stamped with the request id and tenant.
  • Security events logged include tenant_host_mismatch, acting_as_started/acting_as_ended, acting_write_blocked, platform_access_denied, password_reset_*, password_changed, share_passcode_failed and the Mongo-injection warning.
  • The log store is one store for every workspace, so reading it (/api/observability/query and /streams) requires a platform operator. A workspace admin used to be able to run arbitrary queries across all agencies.
  • The workspace audit trail (ActivityLog) records who did what to a record. An acting operator cannot write to it because the session is read-only.

Policy text changes with the code. frontend/src/pages/Legal.jsx (privacy, terms, cookies, refunds) makes factual claims: cookie names, retention periods, who receives data, the export and delete buttons. A change to any of those changes the policy text in the same commit. LEGAL_UPDATED in Legal.jsx and LEGAL_VERSION in backend/utils/legalVersion.js (currently 2026-09-26) move together; the latter is what an accepted invite records, so an acceptance names the text the person actually saw. Business identity (legal name, address, GSTIN, grievance officer) lives only in BUSINESS in frontend/src/utils/marketingCopy.js; null fields are not printed, so never fill one with a guess.

Verified against code: the three cookies and their lifetimes; 180-day security records; 90-day notifications and search history; password storage as salted hashes; message encryption; profile deletion removing name, email, phone and address immediately; the Profile "Download my data" button. The workspace-closure promise ("deleted within 90 days of the request") and the backups sentence are operational commitments with no code behind them.

What is not protected

Read this list before relying on a control above.

  • Password changes end other sessions. Reset, self-change and an admin setting an employee's password all empty the stored refresh tokens, and /refresh rejects any refresh token issued before passwordChangedAt. A self-change keeps the calling device signed in on a fresh token pair. Access tokens already issued stop working at once for the same reason.
  • Isolation is application-level. There is no per-tenant database, row-level policy or encryption key. A bug that bypasses the plugin (a raw driver call, an aggregation stage the plugin cannot scope) is cross-tenant. The tests and the "throw rather than guess" design reduce this; they do not remove it.
  • Share and upload URLs are bearer credentials. Anyone with a share token sees the shared properties until it expires or is revoked. Passcode guesses are limited only by the per-IP shareRateLimit (60 per 15 minutes). Listing photographs and avatars under /uploads/ are served statically with no session (share pages need them); their names are not guessable in practice but they are not access-controlled.
  • Webhook SSRF is a guard, not a guarantee. Literal private addresses are blocked; a public hostname that resolves to a private address is not.
  • Cloudinary uploads bypass server validation. The unsigned preset accepts what Cloudinary accepts. Restrict the preset's folders and formats in Cloudinary.
  • Sockets are authenticated at connect time only. A connection stays up after its access token expires, and a user disabled mid-connection keeps the open socket until it drops.
  • Single-instance defaults. Without REDIS_URL, rate limits and caches are per process (see above). The scheduler is safe on many instances (it takes Mongo leases), the limiter is not.
  • Dev-only helpers. /api/auth/clear-rate-limit was removed: it only returned a message and never reset anything.
  • No MFA, no SSO, no IP allowlists are implemented. Login protection is the password policy, lockout and rate limiting.
  • Backups hold personal data. Erased records remain in older dumps until the retention count rolls them off (BACKUP_RETENTION_COUNT, default 7).
  • A public contact form (POST /api/contact) and client log ingest (POST /api/observability/logs) accept anonymous input; both are rate limited and neither is CSRF-protected by design.
  • Dependencies are audited in CI with npm audit --omit=dev --audit-level=high, advisory only (continue-on-error), so a new advisory is visible but does not block a merge.
