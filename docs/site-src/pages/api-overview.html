Base URL and transport

  • All routes are under /api. The API and the built web app are served by the same Express process in production (frontend/dist), so the web app is same-origin. In development the Vite server on port 5173 proxies /api and /uploads to localhost:3000 (frontend/vite.config.js), so VITE_API_URL is empty. A split deployment sets VITE_API_URL and must list the app's origin in FRONTEND_URL / ADMIN_URL / EXTRA_CORS_ORIGINS.
  • Bodies are JSON (Content-Type: application/json, 10 MB limit) except uploads (multipart/form-data). Responses are JSON and gzip-compressed.
  • The generated, always-current endpoint reference is under API reference. It is built from the live router and the same Joi schemas that validate requests (backend/utils/openapi.js), so it cannot drift; never hand-edit docs/openapi.json. A workspace admin can also fetch it from a running server at GET /api/docs/openapi.json, or regenerate the file with npm run docs:openapi in backend/.

Success responses

There is no single success envelope. Three shapes exist; check the reference for the endpoint you call.

  1. Helper envelope (sendSuccessResponse): { "success": true, "statusCode": 200, "message": "...", "data": ..., "timestamp": "ISO" }. Used by tenant, platform, share, invite, health and most newer controllers.
  2. Hand-written: { "success": true, "data": ... }, and for lists { "success": true, "data": [...], "page": 1, "limit": 20, "total": 134 } (e.g. GET /api/clients, POST /api/clients answers 201 { success, data }).
  3. Top-level fields: sign-in and refresh spread the user document next to success; uploads answer { success, url } or { success, urls }.

In every shape a boolean success is present, and failures always use the error envelope below.

Errors

Every failure answers one shape. code is the contract; message is for a person and may be reworded or translated. Branch on code.

{
  "success": false,
  "statusCode": 409,
  "code": "VERSION_CONFLICT",
  "message": "This record was changed by someone else while you were editing it.",
  "type": "conflict",
  "details": { "currentUpdatedAt": "2026-10-01T09:12:44.000Z" },
  "requestId": "6c1f0f63-6a63-4d0b-9d0c-2f3d8e1a5b77",
  "timestamp": "2026-10-01T09:13:02.114Z",
  "path": "/api/clients/65f..."
}

Optional fields: type (validation, authentication, authorization, not_found, conflict, rate_limit, database), field (the offending input), details. Hand-written res.status(4xx).json({ success:false, ... }) responses still get code and requestId added by middleware/errorEnvelope.js. Quote requestId (also in the X-Request-Id response header) in a bug report; the logger stamps it on every line. In production an unexpected 500 returns a generic sentence and the request id, never the internal message.

A CastError and a duplicate-key error are translated for you: a bad id is 404 INVALID_ID; E11000 is 409 DUPLICATE with a message like "Email already exists". Sign-in failures are intentionally uniform (401 "Invalid email or password").

Paging, sorting and filtering

  • Query: ?page=1&limit=20&sort=field:asc|desc. utils/listQuery.js turns untrusted values into safe numbers: non-numeric or non-positive page/limit fall back to defaults (page 1, limit 20 unless the endpoint sets another), and limit is capped at 500. sort is an allowlist per endpoint; anything else falls back to the endpoint's default, with _id always the final tie-breaker so rows do not repeat or vanish across pages.
  • Response: { success, data: [...], page, limit, total }. Sorting and paging happen in the database, so sort by the server (sort=), never by re-sorting one page.
  • Bare arrays when page is absent. GET /api/owner/list and GET /api/buyer-requirements page only when page is passed; without it they return a bare array, which the mobile app and the listing form read. Do not assume a list is wrapped.
  • Clients list sorts by name, score, temperature, status, priority, budget, nextFollowUp, email, createdAt, updatedAt (default updatedAt desc) and filters by q (text search), status, contactType, tag, temperature (hot|warm|cold) and, for admins, assignedTo. A non-admin is always narrowed to their own leads whatever the query says.
  • Listings: search is one service (backend/search/listingSearch.js) behind GET /api/listing/search; use GET /api/listing/facets for counts over the whole filtered set (a header count must never be computed from a page).

X-Total-Count and X-Rate-Limit-Remaining are listed in the CORS exposedHeaders but no controller sets them today. Read the total from the body, and rate-limit state from the standard RateLimit-* headers.

Edit conflicts (409)

Listing and client edits accept expectedUpdatedAt (the updatedAt the form loaded). The write is conditional on it, and if someone saved in between, the answer is 409 VERSION_CONFLICT with details.currentUpdatedAt. The form offers "Load their version" or "Keep mine" (resend without the guard). A caller that sends no version (the mobile app, scripts) keeps last-write-wins. An unparseable value is a 400, not a silent skip. Client updates stay a document save() with $where, so pre-save hooks and score recalculation still run.

Other 409s answer with a count instead of proceeding, and the UI turns them into a choice with ?force=true: deleting a category in use, removing a category field that holds values, and creating a lead whose email or phone already exists (POST /api/clients returns data.duplicate and canForce: true; ?force=true creates it anyway).

Plan limits (402)

Plan limits (maxUsers, maxListings, maxImportRowsPerMonth, maxStorageMb; a value of 0 or less means unlimited) gate creation only, never reads: a workspace that went over after a downgrade keeps full access to what it has. A blocked create answers 402 PLAN_LIMIT and a message saying what to do next (for example the plan name, cap and a hint). GET /api/tenant/usage shows usage against caps, with a nearLimit flag at 80%. Import row allowances reset monthly (job import-usage-reset).

Rate limiting

429 responses use the error envelope with code: "RATE_LIMITED", plus RateLimit-* and Retry-After headers. The default general ceiling is 1000 requests per 15 minutes per user (per IP when signed out), 20 per 15 minutes on credential endpoints. Full table: Security. Honour Retry-After; the web client shows "Too many requests. Please wait a moment and try again."

Response encryption (optional)

When the server runs with ENCRYPT_API_RESPONSES=true and API_RESPONSE_SECRET, middleware/encryptResponse.js replaces every JSON body under /api (except /api/health* and /api/observability*; the rate limiter's 429s are emitted before it) with:

{ "_enc": true, "iv": "<base64, 12 bytes>", "data": "<base64: ciphertext || 16-byte GCM tag>" }

The key is SHA-256(API_RESPONSE_SECRET); the cipher is AES-256-GCM with no additional data. The error envelope's code and requestId are added before encryption. If encryption throws, the server falls back to plaintext rather than breaking the response. The web client decrypts in parseJsonSafely when VITE_API_RESPONSE_SECRET (the same value, baked into the bundle at build time) is set; otherwise it logs "Received encrypted response but VITE_API_RESPONSE_SECRET is not configured" and treats the body as empty. ENCRYPT_API_RESPONSES is a startup flag: it is read once, at import.

// Node decode of one response body
import crypto from 'node:crypto';
const key = crypto.createHash('sha256').update(process.env.API_RESPONSE_SECRET).digest();
function decode({ iv, data }) {
  const buf = Buffer.from(data, 'base64');
  const d = crypto.createDecipheriv('aes-256-gcm', key, Buffer.from(iv, 'base64'));
  d.setAuthTag(buf.subarray(buf.length - 16));
  return JSON.parse(Buffer.concat([d.update(buf.subarray(0, buf.length - 16)), d.final()]).toString('utf8'));
}

This is not a confidentiality control: the secret ships in the public JavaScript bundle. Treat it as response obfuscation on top of TLS. The mobile app has no decoder, so leave encryption off if the mobile app must work.

File uploads

Images and voice notes in the web app go to Cloudinary directly from the browser. The backend accepts multipart uploads on POST /api/upload/single (field image, 10 MB), /multiple (field images, up to 6, 10 MB each) and /audio (field audio, 25 MB), and documents on /api/documents. Types are decided by magic bytes, never by the declared Content-Type (Security). Do not set Content-Type yourself; let the client add the boundary. Results: 201 { success, url: "/uploads/..." }. Documents are downloaded through GET /api/documents/file/:filename, not /uploads.

curl -X POST http://localhost:3000/api/upload/single \
  -b cookies.txt -H "X-CSRF-Token: $CSRF" \
  -F 'image=@photo.jpg'

Outbound webhooks

Admins manage endpoints under /api/webhooks (list, create, update, delete, POST /:id/rotate-secret, POST /:id/test, GET /:id/deliveries). Subscribe to event names or * (stored as-is, so a workspace subscribed to everything keeps getting new event types). The vocabulary lives in WEBHOOK_EVENTS (models/webhook.model.js):

lead.created, lead.updated, lead.assigned, lead.deleted, deal.created, deal.stage_changed, listing.created, listing.updated, task.created, task.completed, buyer.created, share.viewed.

Delivery. Emitting only writes a row inside the request that caused it, so a slow or dead endpoint never slows or fails the user's action. The scheduler (job webhook-delivery, every minute) does the POST with a 10-second timeout and no redirects. Retries wait 10 s, 1 min, 5 min, 30 min (five attempts in total); an endpoint that fails 10 times in a row disables itself. Delivery rows are kept 30 days.

POST https://your.endpoint/hook
Content-Type: application/json
User-Agent: RealVista-Webhooks/1
X-Webhook-Event: lead.created
X-Webhook-Delivery: 65f0c1...
X-Webhook-Timestamp: 1790000000
X-Webhook-Signature: sha256=3b1f...

{ "event": "lead.created", "sentAt": "2026-10-01T09:12:44.000Z",
  "data": { "id": "...", "name": "Asha Verma", "email": "", "phone": "9876543210",
            "status": "lead", "source": "", "assignedTo": "..." } }

The signature is HMAC-SHA256(secret, timestamp + "." + rawBody) in hex, prefixed sha256=, computed over the exact bytes sent. The timestamp is inside the signed string so a captured delivery cannot be replayed later against a receiver that checks it. The secret has the form whsec_<48 hex>; it is stored readable on purpose, since the receiver needs the same value.

// Express receiver: verify before trusting anything in the body
import crypto from 'node:crypto';
import express from 'express';

const SECRET = process.env.REALVISTA_WEBHOOK_SECRET;   // whsec_...
const app = express();

app.post('/hook', express.raw({ type: 'application/json' }), (req, res) => {
  const ts = req.get('X-Webhook-Timestamp');
  const sig = req.get('X-Webhook-Signature') || '';
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return res.sendStatus(400);   // replay window

  const expected = 'sha256=' + crypto.createHmac('sha256', SECRET)
    .update(`${ts}.${req.body.toString('utf8')}`).digest('hex');
  const ok = sig.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected));
  if (!ok) return res.sendStatus(401);

  const { event, data } = JSON.parse(req.body.toString('utf8'));
  // handle event ...
  res.sendStatus(200);          // any 2xx counts as delivered
});

Use the raw body, not a re-serialised object: re-stringifying changes bytes and breaks the signature. Webhook URLs must pass the SSRF guard (public host, https in production): Security.

Worked example: sign in, then create a lead

The sign-in response already sets csrf_token, so the explicit /api/auth/csrf call is only needed by clients that cannot read cookies. Replace acme with your workspace slug (omit x-tenant on a single-workspace deployment).

BASE=http://localhost:3000

# 1. Sign in (sets access_token, refresh_token, csrf_token)
curl -s -c jar.txt -X POST $BASE/api/auth/signin \
  -H 'Content-Type: application/json' -H 'x-tenant: acme' \
  -d '{"email":"owner@acme.in","password":"Secret@123"}'

# 2. Get the CSRF token (works for any client; echoes the cookie value)
CSRF=$(curl -s -b jar.txt -c jar.txt $BASE/api/auth/csrf | node -pe 'JSON.parse(require("fs").readFileSync(0)).csrfToken')

# 3. Create a lead
curl -s -b jar.txt -X POST $BASE/api/clients \
  -H 'Content-Type: application/json' -H "X-CSRF-Token: $CSRF" \
  -d '{"name":"Asha Verma","phone":"9876543210","email":"asha@example.com","source":"99acres","budget":{"min":4000000,"max":6000000,"currency":"INR"}}'
# 201 { "success": true, "data": { "_id": "...", "name": "Asha Verma", "status": "lead", ... } }

# 4. The same phone or email again answers 409 (data.duplicate, canForce: true);
#    ?force=true creates the second record anyway
curl -s -b jar.txt -X POST "$BASE/api/clients?force=true" \
  -H 'Content-Type: application/json' -H "X-CSRF-Token: $CSRF" \
  -d '{"name":"Asha Verma (second number)","phone":"9876543210"}'

# 5. Read it back, paged and sorted
curl -s -b jar.txt "$BASE/api/clients?page=1&limit=20&sort=createdAt:desc&status=lead"

The create schema (clientValidation.create) requires only name (2 to 120 characters). status is one of lead, contacted, qualified, proposal, negotiation, won, lost; temperature is hot|warm|cold; unknown fields are dropped. The assignee is chosen by the workspace's lead-assignment rule when you do not name one, and a non-admin cannot assign to someone else. Creating a lead also fires the lead.created webhook and computes the lead score.

In production the cookies are Secure, so use https://; curl then needs the cookie jar from an https session.
