Middleware order

createApp() in backend/app.js is the one place the pipeline is assembled. The order is tested (tests/requestPipeline.test.js) because several of these steps only work in a particular sequence.

Request ids

utils/logContext.js gives each request an id (requestContext middleware, mounted first in app.js). A caller-supplied X-Request-Id is kept if it matches ^[A-Za-z0-9._:-]{8,64}$; otherwise a UUID is generated. It is set on req.id, returned as the X-Request-Id response header, repeated as requestId in every error body, and stamped by the logger (with the tenant and user) on every line written while the request is in flight, so a "ref" a user reads out finds the log. utils/requestContext.js is a thin wrapper kept for callers that only want getRequestId(); there is one store, not two.

It is a separate AsyncLocalStorage from the tenant context on purpose: the id exists before the tenant is resolved (and for routes that have none), and the two must not be able to overwrite each other. Jobs and sockets get their own context with runWithLogContext(); outside any context the id is null.

One error shape

Every failure answers:

{
  "success": false,
  "statusCode": 409,
  "code": "VERSION_CONFLICT",     // the contract - branch on this
  "message": "This record was changed by someone else while you were editing it.",
  "type": "conflict",             // optional
  "field": "email",               // optional
  "details": { "currentUpdatedAt": "..." },   // optional
  "requestId": "6f1c...",
  "timestamp": "2026-10-02T09:15:00.000Z",
  "path": "/api/listing/update/<id>"
}

code is the contract; message is for a person. A client switching on "Category in use" broke the day the sentence was improved, and wording also changes with language. Codes are additive: older fields stay and code and requestId are added.

How to raise an error

  • Throw AppError (new AppError(message, statusCode, isOperational = true, code?)) or a subclass from utils/error.js: ValidationError (400, VALIDATION_FAILED, takes a field), AuthenticationError (401), AuthorizationError (403), NotFoundError (404), ConflictError (409), VersionConflictError (409, VERSION_CONFLICT, takes details), RateLimitError (429), DatabaseError (500). The legacy helper errorHandler(status, message) returns an AppError.
  • Wrap async handlers in asyncHandler so a rejection reaches next(err).
  • A hand-written res.status(4xx).json({ success: false, ... }) still works: middleware/errorEnvelope.js adds code (from the status) and requestId to any success: false body with status >= 400, leaving a code that is already present alone. About a hundred call sites (upload limits, the rate limiter, route guards) write errors themselves; rewriting each would be a hundred chances to change a message a client depends on.
  • For a 409 the controller attaches details to say what the conflict is about (how many listings use the category, which fields still hold values). globalErrorHandler passes details through; dropping it once left the UI unable to offer the ?force=true choice.

What classifyError does

One pass turns any thrown value into { status, code, type, message, field, details }. (There used to be two passes that disagreed: the first mapped a bad ObjectId to 404 with type "validation", the second rewrote the message.)

Validation

Every POST/PUT/PATCH needs validateBody(schema) (middleware/validation.js, Joi). It validates with abortEarly: true and stripUnknown: true, reports the first problem as a ValidationError with the dotted path in field, and replaces req.body with the cleaned value.

stripUnknown drops any field the schema omits. A field the controller reads but the schema lacks is silently lost. When you add a field to a controller, add it to the schema in the same change. (This is also why expectedUpdatedAt appears in listing and client update schemas.)

The returned middleware is a function named validateBody carrying its .schema. That lets two tools find it: tests/validationCoverage.test.js walks the live router and fails on any write route with no validateBody on its stack unless it is in the UNVALIDATED list with a reason (multipart uploads, spreadsheet imports, cookie-only session endpoints, routes whose only input is a URL id), and utils/openapi.js documents the request body from the very schema that enforces it. Shrink that list as routes gain schemas; never add to it to make a new route pass. Write the schema.

User text and regular expressions

User text never goes into a regex raw. Use utils/escapeRegex.js: escapeRegex, containsInsensitive and equalsInsensitive. The text is a literal to find, never a pattern. Without this a stray ( was a 500, a.* matched everything, and (a+)+$ could pin a database thread on catastrophic backtracking. They String()-coerce the input first, because Express parses ?q[$ne]=x into an object and an object must reach a query only as its string form.

Sanitising: why the order matters

  • The sanitisers originally ran before the body was parsed, when req.body was still undefined, so {"email": {"$ne": null}} reached controllers untouched and only query strings were cleaned. The body is now parsed first and then mongoSanitization strips operators from body, query and params.
  • allowDots: true because real bodies carry dotted keys: an import's column mapping is keyed by the spreadsheet's own header text ("Phone no."), which replacing the dot would corrupt.
  • xssProtection touches query and params only. Bodies carry intentional HTML (email templates up to 100 KB, report templates, a note saying "<3 BHK"), and escaping on the way in would corrupt what the user saved. Escaping belongs on output: React escapes everything it renders, and mail templates are rendered through utils/emailTemplates.js (named variables only, no expression syntax; HTML sanitised with a whitelist when saved).

CSRF

Authentication is cookie-only and, in production, session cookies are sameSite: 'none' so the app can be served from a different origin than the API. That tells the browser to attach cookies to cross-site requests, which is precisely when a CSRF token becomes mandatory. CORS does not cover it: a cross-origin form POST with application/x-www-form-urlencoded is a CORS "simple request", sent without a preflight, with cookies, and Express parses it.

middleware/csrf.js implements a double-submit token. A random token lives in a readable cookie csrf_token (30 days, httpOnly: false); same-origin script reads it and echoes it in the X-CSRF-Token header. Another origin cannot read our cookies and cannot add a custom header without a preflight that CORS refuses. It is deliberately not a secret: it proves same-origin, not identity. It is minted at sign-in (issueCsrfToken) and on session reissue, and GET /api/auth/csrf echoes it to a caller.

The check is skipped for: safe methods (GET/HEAD/OPTIONS); public writes derived from security/publicRoutes.js (so exemptions cannot drift from the access allowlist); and requests with neither an access_token nor a refresh_token cookie (nothing ambient to forge, and the route's own guard then answers 401 instead of a confusing CSRF error). Comparison is constant-time. The frontend's apiClient attaches the header; the generated API reference marks every guarded write with it.

Because the global limiter runs before any route's verifyToken, req.user is never set yet; the user id is decoded from the cookie directly. An invalid token falls back to the IP: this chooses a bucket, it authenticates nothing. Multi-instance: the limiter counts in process memory by default, so on a PM2 cluster a "20 per 15 minutes" limit is really 20 times the number of instances. With REDIS_URL set, all limiters share one RedisStore (prefix rl:). See Redis.

Route access guard

Access control lives at three levels (a guard on the route, router.use(verifyToken) on a whole router, app-level middleware), so no single file answers "is this endpoint public?". The failure worth guarding is narrow: someone adds a route and forgets the guard, and it is public without anyone deciding that.

backend/security/publicRoutes.js lists only the endpoints that are public on purpose, each with a why: health probes, sign-in/refresh/CSRF/password reset, invite open and accept, workspace config/lookup/features, the share link open, the contact form, unsubscribe, client log ingest, and the SPA fallback. tests/routeAccess.test.js walks the live router and fails if a mounted route is neither guarded (verifyToken, tryVerifyToken, requireAdmin, requirePermission, requirePlatformAdmin, canCreateListing) nor listed, if a listed entry no longer exists, if a public route lacks a reason, if any /api/platform route lacks the platform guard, or if a write has no session requirement.

If the test fails on a new route, add the missing guard. Do not add the route to the allowlist unless it is genuinely meant to be public, and then say why. The same list drives the CSRF exemptions and the "Public" marker in the generated API reference.

Related rule: the property book is not public. Anonymous browsing was removed; nothing about a listing, category or property type is reachable without a session. Sharing outside the agency goes through /api/share and the public GET /api/share/open/:token, where the token is the credential.

Edit conflicts (409 VERSION_CONFLICT)

Listing and client edits send expectedUpdatedAt (the updatedAt the form loaded). The server makes the write conditional on it: listings put it into the update filter so the check and the write are one atomic operation; client updates remain a document save() with $where: { updatedAt }, so pre-save hooks and calculateScore() still run. If someone saved in between, the answer is 409 VERSION_CONFLICT with details.currentUpdatedAt. The form then shows EditConflictNotice ("Load their version" or "Keep mine", which resends without the guard); it is inline because the listing form hosts a Leaflet map and a modal would fight its z-index.

A caller that sends no version (the mobile app, scripts) keeps last-write-wins. An unparseable value is a 400 rather than a silent skip, so a client that meant to guard its edit finds out it did not. Joi's date() hands over a Date; parseExpectedUpdatedAt avoids round-tripping it through a string, which would drop milliseconds and make every guarded save "conflict".

Paging and sorting

List pages sort and page on the server: the page sends sort=key:asc|desc&page=&limit= and reads total from the response. Sorting a page of results sorts the wrong set. On the backend use utils/listQuery.js:

  • parsePaging(query, { defaultLimit = 20, maxLimit = 500 }) returns { page, limit, skip }. Non-numeric or non-positive values fall back to defaults, so ?page=abc no longer produces a NaN skip and a 500, and limit is capped at 500 (high enough for Calendar's 500 tasks and Reports' 200 clients, low enough that no request returns a whole collection).
  • parseSort(raw, allowed, fallback) takes an allowlist mapping public sort keys to stored paths; anything else falls back to the endpoint default. _id is always appended as the final key so equal rows keep a stable order across pages.
  • /owner/list and /buyer-requirements page only when page is passed; without it they return a bare array, which the mobile app and the listing form read.

OpenAPI generation

The API description is generated, never hand-edited (backend/utils/openapi.js). It walks the mounted router for paths, converts the Joi schema attached to each validateBody into the request body schema, and derives security from the guards on each route's stack (public routes carry the why from publicRoutes.js as a "Public:" description). It does not know response bodies (controllers build them by hand), so every operation documents the shared error shape and leaves success open.

  • npm run docs:openapi (from /backend) writes docs/openapi.json. It needs no database; it registers tenancy, builds the app and walks the router.
  • GET /api/docs/openapi.json serves the same document to a workspace admin (verifyToken and requireAdmin), built once per process on first request.
  • The API reference pages in this site are built from docs/openapi.json.

Health and readiness

  • GET /api/health/health, /ready, /live, /startup, /detailed and /metrics are public probes. They report up/down and version only. pid, Node version and heap sizes were removed from the public health route as reconnaissance; /metrics is the place for numbers and takes a bearer METRICS_TOKEN when set.
  • /ready answers 503 while shutting down (see shutdown) and reports Redis as connected, degraded or not_configured without failing readiness over it.
